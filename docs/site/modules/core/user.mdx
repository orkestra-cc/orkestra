# user

Account identity: the per-tier user collections, profile fields, the global **system role**, OAuth link bookkeeping, and the avatar pipeline. A leaf module with no dependencies — everything else reaches it through `iface.UserProvider` rather than importing it.

It deliberately does *not* own passwords, sessions, JWTs, or org memberships. Those belong to [auth](/modules/core/auth) and [tenant](/modules/core/tenant).

## What it owns

- **Two user collections, one per tier** — `operator_users` and `client_users`. Email uniqueness is scoped *per collection*, so the same address may legitimately exist as both an operator account and a client account: one human running an internal staff role and an external client account are two different principals.
- **The system role** — `User.Role`, one of `super_admin` › `administrator` › `developer` › `manager` › `operator` › `guest`. This is the value a token carries as `srole` — but only until it changes: the stored row is the authoritative copy, and every guard here reads the row rather than the claim, which can be a whole access-token lifetime out of date. Org-scoped roles are a different thing entirely and live in [authz](/modules/core/authz) as role bindings.
- **The avatar pipeline** — the reference consumer of the [object-storage seam](/sdk/object-storage): presign, upload direct to storage, commit. Sources are `uploaded`, `initials`, or a linked OAuth provider's picture.
- **Three registry providers** — `ServiceUserService` (canonical, operator-tier), plus `ServiceOperatorUserProvider` and `ServiceClientUserProvider` for audience-aware consumers.

Each per-tier provider also implements the additive `iface.InitialPasswordSetter` capability, without changing `iface.UserProvider`. `SetPasswordHashIfUnset` persists a first hash only when a live user's stored `passwordHash` is absent or empty, setting `passwordUpdatedAt` and `updatedAt` in the same atomic write. An existing hash returns `iface.ErrPasswordAlreadySet` and leaves the hash and timestamps unchanged; a missing or soft-deleted user returns `iface.ErrUserNotFound`. Two concurrent initial writes yield one success and one conflict. The existing `UpdatePasswordHash` keeps its overwrite behavior for password changes and resets; auth still owns hashing and self-service HTTP policy.

## Routes

Every admin route is gated by one per-action `user.*` key, evaluated at **global scope** (`RequireSystemPermission`: users are platform rows, so a tenant membership never counts, and no `X-Tenant-ID` is needed). The same keys gate both tiers — a user admin is a user admin whichever collection the row lives in.

| Gate | Operator tier | Tier-2 client admin (`/v1/admin/client-users…`) | Step-up |
|---|---|---|---|
| `user.read` | every `GET` under `/v1/users` | list, get | — |
| `user.create` | `POST /v1/users` | create, invite, `invite/resend`, `resend-verification` | — |
| `user.update` | `PUT /v1/users/{id}` | `PATCH …/{id}` | **5 min** |
| `user.update` | — | `send-password-reset` (mails an expiring link to an existing user; nothing changes until redeemed) | — |
| `user.delete` | `DELETE /v1/users/{id}` | `DELETE …/{id}` | **5 min** |
| `user.avatar.self` | `/v1/me/avatar/presign-upload`, `/v1/me/avatar/commit`, `/v1/me/avatar/source` — on **both** tiers | | — |
| `user.self` | `GET /v1/me/preferences`, `GET`/`PUT /v1/me/preferences/{module}`, `GET /v1/me/profile-sections` — on **both** tiers | | — |

**Who holds what.** At global scope a platform role conveys its seeded permission set ([authz rule 2b](/modules/core/authz#how-a-decision-is-made)): `super_admin` and `administrator` everything; `manager` read, create and update — so a manager runs the operators without being a platform administrator; `operator` and `guest` read only. `system.users.admin` is no longer a gate on this surface. If your deployment enforces Cedar for `system.users.admin` (`CEDAR_ENFORCE_ACTIONS`), list `user.read`, `user.create`, `user.update` and `user.delete` instead: the same restrictions follow them — no user management from a public IP in production, and a second factor for the roles that can write users.

**Hard mutations sit behind a step-up.** Updating or deleting a user (operator or client tier) requires an MFA proof fresher than 5 minutes, so a long-lived admin session cannot destructively mutate platform state hours after the last verification. Reads, creates and the mail triggers stay on the plain permission gate.

| Key | Grants |
|---|---|
| `user.read` | List and read users |
| `user.create` | Create and invite users |
| `user.update` | Update user profiles, roles and status; send a password reset |
| `user.delete` | Delete users |
| `user.self` | Read and save your own per-module preferences; discover your profile sections |
| `user.avatar.self` | Manage your own avatar |

## Guards worth knowing

These refuse the request rather than trusting the caller, and each returns a distinct error code:

- **Last administrator** — no delete, deactivation, or role demotion may leave zero live, active platform administrators (`user.last_admin_forbidden`). The quorum check counts active `super_admin` + `administrator` rows and is best-effort under concurrent edits. It is **operator-only**: a Tier-2 client user is never a platform administrator, so the quorum is not mirrored onto that tier.
- **Self-delete** — an admin cannot delete their own account (`user.self_delete_forbidden`).
- **Target tier** — nobody may update or delete a user whose *current* role sits above their own (`user.target_tier_forbidden`): a manager holding `user.update` still cannot rename, re-email, deactivate or delete an administrator. Equal tier passes. It runs on every update and delete on both tiers, profile-only patches included, so it costs one read of the target's row; when that row cannot be read the request is refused (`500 user.role_lookup_unavailable`) rather than written blind.
- **Role escalation** — no one may assign a role above their own tier (`user.role_escalation_forbidden`). An administrator can assign administrator but never super_admin. It covers five endpoints: the operator create and update, and the client-user create, invite and patch. The caller's tier is read from the **database**, not from the token — reading the claim would let a demoted administrator keep minting administrators until their last token expired. A caller with no authenticated identity fails closed with a refusal; a caller whose row is absent or unreadable fails closed with `500 user.role_lookup_unavailable`, never a fallback to the claim.
- **Revoking access ends sessions.** Deactivating, soft-deleting, **or changing a user's system role** calls `iface.SessionTerminator` — refresh tokens revoked, session docs flipped, every `sid` pushed into the Redis revocation set. Before this existed a "disabled" account kept working for the full refresh-token lifetime. On the deactivate and delete paths the call is deliberately best-effort and silent: the state change is already persisted, and failing the operator's request would report a deactivation that did in fact happen.
- **A role change propagates.** Changing a system role also retires that user's cached permission verdicts, so the next decision uses the new role rather than one held for the cache's TTL. Neither the cache retirement nor the session termination can *refuse* the change — refusing a demotion would leave the old role in force indefinitely instead of for a minute — so what did not happen is recorded in the audit row (`cache_invalidated`, `sessions_terminated`) instead. The equivalent client-tier patch needs no cache retirement (a client user's role never enters permission evaluation) and marks that fact explicitly rather than leaving it implied.

## Profile sections and per-module preferences

Two seams let a module reach the user pages without the user module knowing it:

- **Profile sections** (`module.HasProfileSections`). A module declares the sections it contributes — key `<module>.<name>`, a label key in its own i18n namespace, an optional permission, the surfaces (`self`: the user's own profile and settings; `admin`: an administrator's view of a user). The admin SPA renders contributions through its slot system (slot ids `user.profile.sections`, `user.adminProfile.sections`, `user.settings.sections`); `GET /v1/me/profile-sections` and `GET /v1/users/{id}/profile-sections` list the same catalog for other clients, filtered to enabled modules and to the sections whose permission the caller holds in the request tenant, or at global scope when the request resolves no tenant. That is the scope the SPA checks and the one the module's own routes enforce: at global scope a platform role conveys every `.read`/`.self` key, so a global check would list sections the module then refuses.
- **Per-user preferences** (`module.HasUserPreferences`). A module declares preference fields in the `ConfigField` vocabulary of its admin config (string, bool, int, duration, enum, stringList; no secrets, no record lists). The user module keeps one `user_preferences` document per user and module and serves `GET /v1/me/preferences` (every enabled module with a schema, values with defaults filled), `GET /v1/me/preferences/{module}` and `PUT /v1/me/preferences/{module}` (PUT semantics; every key must be declared and every value valid — `422 user.preferences.invalid` lists every problem; `404 user.preferences.module_unknown` when the module declares nothing or is disabled). The settings page renders every declared schema with the generic config form, so a module ships no settings component. Preferences are personal: there is no admin route to read or write another user's.

## Soft delete and the email alias

Deletes are soft — `DeletedAt` is stamped, the row stays. But the unique email index still matches soft-deleted rows, so a plain soft delete would permanently block that address from re-registering. `SoftDeleteAndAliasEmail` is the escape: it stamps `deletedAt` *and* atomically rewrites the address to an orphan alias, preserving the original on `originalEmail` for audit. That frees the unique index so the same human can sign up again from scratch.

## GDPR

Registers an `iface.PIIProducer` for the subject `user`. Export returns the profile projection plus the user's per-module preferences (`preferences`, keyed by module); erasure deletes the preference rows in both modes. The profile export — never the password hash or PIN, which are server secrets rather than portable personal data. Erasure **anonymizes** by default: the UUID survives so foreign references stay valid, the email is aliased and the profile blanked, producing the tombstone the [compliance](/modules/core/compliance) retention job later hard-deletes.

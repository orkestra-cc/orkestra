# llm

Language-model access for the platform: **credentials**, a **model catalog**, per-user **grants**, and the `iface.LLMGateway` that other modules consume. Added to the always-loaded core by [ADR-0022](/adrs/core-llm-module) — whose API key is used, which models exist, who may use them and how much they may spend are questions every product rebuilds, so the base answers them once. Tier-1 only: every row belongs to an internal organization.

The module boots with zero credentials and zero models. It is healthy in that state and the gateway answers `ErrLLMNotConfigured` until an active model exists, in the same spirit as `notification` booting in `noop`.

## What it owns

Nine collections. Eight are scoped to an internal organization (`tenantId`); `llm_installation` is the one exception:

| Collection | Holds |
|---|---|
| `llm_credentials` | An API key per provider: `name`, `provider`, `baseUrl`, the sealed `secret` envelope, the display-only `secretLast4`, `status`, and who created it. Names are unique per organization. |
| `llm_models` | A configured model: provider and model ID, the **capabilities** it offers (chat, streaming, tools, structured output, embeddings and dimensions), a `credentialRef`, defaults (temperature, output limit, effort), the **purposes** it serves with a priority each, `access` (`granted` or `everyone`, set only through the grants route) and `status`. Names are unique per organization. |
| `llm_grants` | One row per `(model, user)` pair that may use a model, with who granted it. |
| `llm_usage` | The per-call ledger: who called (user, calling module, purpose), which model and provider answered, who paid (`org` or `user_account`), token counters, latency, outcome (`pending`, `ok`, `fallback`, `error`, `budget_blocked`), an error code and up to eight attempts (counters only). Never a prompt or an output. Kept `usage_retention_days`. |
| `llm_usage_monthly` | One rollup per organization and UTC month: requests, input and output tokens per payer, tokens reserved by calls in flight, and when the warning and exhausted thresholds were crossed. Kept 24 months. |
| `llm_budgets` | At most one per organization: monthly token limit, warning percentage, action (`block` or `warn_only`), extra alert recipients. No document means no limit. |
| `llm_budget_outbox` | Budget alerts waiting for or after delivery, one per organization, month and threshold, with the recipients already delivered. |
| `llm_user_accounts` | A user's linked ChatGPT account (see [Sign in with ChatGPT](#sign-in-with-chatgpt)): label, email, status, whether plan usage was granted, expiry times, and the three sign-in tokens, each sealed in its own envelope. A user may hold several; one is *selected*. |
| `llm_installation` | One document holding this installation's host identifier, which OpenAI asks for once per host. It has no organization: one database deployment is one host. |

### Secrets and the envelope

An API key is **write-only**: it is accepted on create and rotate and never returned. Reads show `hasSecret` and the last four characters (`secretLast4`, and only when the key is at least eight characters long).

The stored form is an envelope `{alg, keyId, keyVersion, schemaVersion, ciphertext}`:

- `alg: kms` — sealed with the per-tenant key of the compliance module's KMS provider, once compliance has injected one. A tenant purge crypto-shreds the credentials with it, including when the organization predates KMS and its key was first created for an LLM credential.
- `alg: local` — AES-256-GCM with the dedicated `LLM_SECRET_ENCRYPTION_KEY` (32 bytes, 64 hex characters).

The associated data is `tenantId|resourceUuid|field|schemaVersion`, so an envelope copied to another tenant, record or field fails to open; an empty part or one containing `|` is refused on seal and open. On the KMS path a ciphertext the provider cannot open (truncated, tampered with, or sealed under another key) is a corrupt envelope, while a crypto-shredded key keeps its own error. The key is decrypted only when a provider request is built, and never reaches a log, a response or an error message.

:::note Missing key
A missing or malformed `LLM_SECRET_ENCRYPTION_KEY` does not stop the boot. The module logs a warning and treats the key as absent: everything works except saving a secret, which answers `llm.secret_key_missing` (503) until a key or a KMS provider exists. In staging and production the environment checker refuses a missing, placeholder or non-64-hex value before the stack starts.
:::

## Permissions

All admin permissions are `System: true` — only the platform system roles inherit them, and no role name appears in the module. The suffix carries the rule:

| Permission | Kind | Grants |
|---|---|---|
| `llm.admin.read` | read | See credentials (redacted), models and grants. A `developer` keeps this in production |
| `llm.credentials.admin` | mutation | Create, rotate, re-point and delete credentials |
| `llm.models.admin` | mutation | Create, update and delete models |
| `llm.grants.admin` | mutation | Decide who may use each model |
| `llm.usage.read` | read | See the usage report — which also carries the budget, so this permission reads the budget too |
| `llm.budgets.admin` | mutation | Set the monthly budget, its action and extra recipients |
| `llm.accounts.admin` | mutation | Force-unlink another member's linked ChatGPT account |
| `llm.models.self` | self | List the models you may use (an organization permission, not a system one) |
| `llm.usage.self` | self | See your own consumption this month (an organization permission) |
| `llm.accounts.self` | self | Link, select and unlink your own ChatGPT accounts (an organization permission) |

Every `.admin` mutation requires a second factor completed in the session — the route itself checks it, independently of whether the policy engine's admin-suffix rule is enforced — and credential, grant and budget changes and the forced unlink of a linked account additionally require a fresh one (step-up, five minutes; a password reconfirm does not count). Your **own** linked-account routes (`llm.accounts.self`) need neither: they only touch your own registrations, like the list of your models. A `developer` is not granted an `.admin` key in production. Each mutation emits an audit event (`llm.credential.created|updated|rotated|deleted`, `llm.model.created|updated|deleted`, `llm.grants.replaced`, `llm.budget.updated`, `llm.credential.tested`, `llm.credential.models_discovered`, `llm.account.link_started|link_denied|linked|selected|unlinked`) once the compliance module has injected the audit sink; the event carries names and counts, never secrets or base URLs.

## Configuration

Settings at `/admin/modules/llm`, in three groups (providers, limits, Sign in with ChatGPT). The module hot-reloads its configuration, so a change applies to the next call without a restart (with one exception, noted on `siwc_mode`); out-of-range values are clamped.

| Key | Default | Env var | Meaning |
|---|---|---|---|
| `allow_hosted` | `false` | `LLM_ALLOW_HOSTED` | Explicit privacy opt-in for hosted providers (`openai`, `anthropic`, `gemini`, `openai_compatible`): prompts and outputs leave the installation. Without it only `ollama` and `mock` can be created, enabled or edited, and existing hosted models stop being offered at once. Disabling a credential or model is always possible |
| `request_timeout` | `60s` | `LLM_REQUEST_TIMEOUT` | Deadline per provider attempt; a consumer may only lower it. A reservation lasts `2 × request_timeout + 60s` |
| `usage_retention_days` | `90` | `LLM_USAGE_RETENTION_DAYS` | Retention of per-call usage rows (31–3650: the current month always stays complete for self usage) |
| `budget_warn_pct` | `80` | `LLM_BUDGET_WARN_PCT` | Default warning threshold for new budgets (0–100) |
| `budget_reserve_output_tokens` | `4096` | `LLM_BUDGET_RESERVE_OUTPUT_TOKENS` | Output tokens reserved against the budget when a model declares none (1–131072). A model's own `budgetReserveOutputTokens` overrides it; sending `0` on create or `PATCH` means no override, so `PATCH` with `0` returns the model to this default |
| `siwc_mode` | `disabled` | `LLM_SIWC_MODE` | `disabled`, `loopback_local` or `hosted_paste` (see [Sign in with ChatGPT](#sign-in-with-chatgpt)). Either mode requires `allow_hosted`; a contradictory combination is refused with `llm.siwc_config_invalid`. Switching **to** `loopback_local` takes effect after a restart (its callback route is mounted at boot); `hosted_paste` and `disabled` apply at once |
| `siwc_paste_port` | `14555` | `LLM_SIWC_PASTE_PORT` | Advanced, `hosted_paste` only. Port (1024–65535) of the `127.0.0.1` address users paste back. Nothing listens on it; change it only if a program on users' machines uses it (the Codex CLI uses 1455) |

`allow_hosted` is a technical control. Before enabling it, document the data flow (categories of prompts and outputs, purpose and legal basis, processor, retention, region and transfer mechanism) in your records of processing.

`loopback_local` also reads the environment variable `OPERATOR_API_URL`, the operator API's public origin (derived from `CONSOLE_HOST` when unset), and requires it to be exactly `http://127.0.0.1:<port>` with an explicit port other than 80 (a browser drops the default port from the address it sends back, so the callback could never match); the development compose file defaults to that.

Endpoint rules: `openai`, `anthropic` and `gemini` have a fixed endpoint and take no `baseUrl`; `ollama` and `openai_compatible` require one; `mock` takes none. In a production-like environment a `baseUrl` must be public HTTPS — loopback, private, link-local, CGNAT, multicast, ULA and other special-use ranges, `.local` and `.internal` names and the metadata host are refused.

## Access model

**Managing is not using.** Holding `llm.models.admin` lets you define a model; it does not let you call it. A user may use a model when:

1. the model is **live**: `active`, its provider is allowed by the configuration read on that call (`allow_hosted` for hosted providers, never `mock` in a production-like environment), and the organization credential it rides on exists and is active; **and**
2. its `access` is `everyone`, **or** the user holds a grant for it.

A model that is not live is invisible to the self list, to `Resolve` and to routing, exactly as if it were disabled: turning `allow_hosted` off, or disabling a credential, takes effect at once for every existing model. An organization whose only active models are not live is *not configured* (`llm.not_configured`).

Who may use a model is decided only on the grants route (`PUT …/grants`, `llm.grants.admin` plus step-up), never by `llm.models.admin`: opening a model to everyone is the widest access change, so it has the strongest gate. The route sets `access` and replaces the complete grant list together, in one database transaction: two administrators saving at the same time end with exactly one of their two requests, never a mix, and a failed save changes nothing. Every listed user must be a member of the organization, or the whole call is rejected and nothing (not even `access`) changes. With `access: everyone` the listed grants are still stored but dormant; they apply again when `access` returns to `granted`. `GET /v1/llm/me/models` and the gateway use the same resolver, so the self list shows exactly what a call may route to.

Routing for a purpose: the candidates are the usable models that declare the purpose and offer the capabilities the request needs, ordered by that purpose's priority (lower wins) then name. The purpose falls back to `default` **only** when no live model of the organization declares it at all; if some model declares it but the caller may not use it, the result is empty (`ErrLLMNoEligibleModel`) rather than a silent move to another purpose. A caller may pin one model; a pin must be among its candidates, so pinning never widens access.

A model billed to the user's own linked account (`credentialRef.kind = user_account`) must use the `openai` provider, cannot offer embeddings and cannot set a temperature or output limit. It is usable by someone who both holds the grant **and** has a usable selected linked account whose plan catalog lists the model; otherwise it is hidden from the self list and `Resolve`, and a direct call answers `llm.user_account_required`, `llm.user_account_reauth_required`, `llm.plan_usage_disabled` or a capability mismatch, so a consumer can tell the cases apart.

## Gateway contract

Addons resolve the gateway from the service registry and ask for a *purpose*; they never see a credential:

```go
gw, ok := module.GetTyped[iface.LLMGateway](deps.Services, module.ServiceLLMGateway)
if !ok {
    return errors.New("llm module not loaded")
}

res, err := gw.Chat(ctx, iface.ChatRequest{
    Purpose:  "summarize", // "" means "default"
    Caller:   "myaddon",   // required: the calling module's name
    Messages: []iface.ChatMessage{{Role: "user", Content: text}},
}, func(ev iface.ChatEvent) error {
    // stream deltas; return an error to abort
    return nil
})
switch {
case errors.Is(err, iface.ErrLLMNotConfigured):     // no active model in this organization
case errors.Is(err, iface.ErrLLMNoEligibleModel):   // models exist, none this caller may use
case errors.Is(err, iface.ErrLLMProviderUnavailable):
}
```

The interface has four methods: `Chat`, `Embed`, `Resolve` (the model `Chat` would pick, without calling it) and `ListUsable`. The registered gateway also implements `iface.LLMAvailabilityProbe`, for checks that run with no user or organization in context, such as a module health check: `HasLiveModel(ctx, purpose, need)` reports whether any organization has a live model that would serve the purpose with the given capabilities. It ignores per-user grants and linked accounts, so `true` does not mean every user can use the model. Message roles are `developer`, `user`, `assistant` and `tool`; system text goes in `ChatRequest.Instructions`. Errors are classified with the `ErrLLM*` sentinels in `pkg/sdk/iface/llm.go`, which a consumer maps to its own error codes. The acting user comes from the request context, and the gateway refuses a tenant that is not internal.

`Options.MaxOutputTokens` must be between 1 and 131072, like every other output limit: it is what the call reserves against the budget. `ChatResult.Usage` and the final `Done` event report the usage of the attempt that answered; after a fallback the ledger and the budget also charge the failed attempts.

The compliance module resolves the same service to inject its KMS provider and audit sink (`iface.KMSProviderSetter`, `iface.AuditSinkSetter`).

## Routing

One `Chat` or `Embed` call goes through these steps:

1. **Candidates** — the usable models for the purpose, as described above.
2. **Reservation** — the estimated input plus the reserved output tokens are reserved against the month's budget and a `pending` ledger row is written, in one transaction. A call that does not fit under `block` is refused here (`llm.budget_exceeded`), before any provider is contacted.
3. **Circuit breaker** — per provider, endpoint, model and credential: three consecutive provider faults open the circuit for 30 seconds, then a single probe call is let through. Only the provider's own faults count (unavailability, provider timeouts, 5xx, a rejected key, an exhausted quota); a caller that hangs up or shortens the deadline, an invalid request, the budget or a capability gap never trips it.
4. **Attempt** — the provider call, bounded by `request_timeout` or the caller's shorter deadline. A streamed answer may stay silent for up to `request_timeout` (at least 30 seconds) before it is cut, so a model that reasons before its first output is bounded by the deadline, not by a shorter idle timer.
5. **Fallback** — on a provider failure the next candidate is tried, but only one billed the same way (`org` or `user_account`): a fallback never changes who pays. Cancellation, deadlines, budget and linked-account errors, an exhausted quota, an invalid request and a failure after output already reached the caller (`llm.partial_output`) are final.
6. **Finalization** — the ledger row records the outcome, the attempts and the real tokens; the month's rollup releases the reservation and adds the tokens to the payer's counters. If the process dies before this, a background reconciler closes the row once its reservation expires, charging the whole reservation.

A call that fails after streaming part of its answer is charged conservatively. When the provider reported usage, the charge is the reported input (the estimate if it is missing) and the larger of the reported output and the emitted text (bytes / 3). Without reported usage, it is the estimated input and the larger of the reserved output and the emitted text. A call whose only failure is the consumer's sink refusing the final `Done` event is a completed call: it is charged its reported usage, and `Chat` returns the sink's error.

## Providers

| Provider | Endpoint | Notes |
|---|---|---|
| `openai` | fixed (Responses API) | Official SDK. Chat, streaming, tools, structured output, embeddings. Models billed to a linked ChatGPT account use a restricted request profile (no embeddings; see [Sign in with ChatGPT](#sign-in-with-chatgpt)) |
| `anthropic` | fixed (Messages API) | Official SDK. No embeddings |
| `gemini` | fixed (Gemini Developer API) | Official SDK. Tool calls carry an opaque `Signature` (Gemini 3 thought signatures) that must be sent back on the next turn |
| `ollama` | `baseUrl` required | Native API. The key is optional (sent as a Bearer token for proxied deployments) |
| `openai_compatible` | `baseUrl` required | Chat Completions wire format for self-hosted servers (vLLM, llama.cpp, LiteLLM, …); the key is optional |
| `tei` | operator environment | **Installation-only.** Embeddings and reranking for `retrieval`; never selectable for an organization model and never listed at `/admin/llm` (see [Installation inference endpoints](#installation-inference-endpoints)) |
| `mock` | none | Deterministic echo for tests and non-production stacks; never selectable in a production-like environment |

Every provider connection re-checks each resolved address at dial time (no private or special-use address in production-like environments), follows no redirect and no proxy, caps response sizes (8 MiB, 32 MiB for embedding calls; OpenAI embeddings are requested base64-encoded), disables SDK retries and never surfaces provider error text: failures become `llm.*` codes. `allow_hosted` gates the hosted providers on the live path and on the admin test, discovery and prompt operations alike.

## Budget

A budget is an **admission control**, not a kill switch. Each call reserves its estimated tokens before it runs; under `block` a call that does not fit the remaining balance (`consumed + reserved + requested > limit`) is refused, under `warn_only` it runs and only alerts. The limit counts input and output tokens of both payers. Real usage can exceed the reservation (a long answer), so consumption can end slightly above the limit.

Alerts go by email to the organization's owners and admins plus the extra recipients still in the organization:

- **warning** when consumption crosses `warnPct` of the limit (the default comes from `budget_warn_pct`; `0` disables it);
- **exhausted** at the first call of the month refused under `block` once consumed plus reserved tokens already reach the warning threshold (or the limit, when `warnPct` is `0`), or when consumption reaches the limit. A single oversized request refused while most of the balance is unused is recorded as `budget_blocked` but sends no exhausted alert, so it cannot use up the month's only one;
- **oversized** at the first call of the month refused under `block` that needs more tokens than the whole limit, when the exhausted alert does not fire. No balance could ever admit such a call: without this alert a budget smaller than one call would block the organization silently.

Each alert is sent at most once per organization and month. It is written in the same transaction that crosses the threshold and delivered from a durable outbox with retries; delivery is tracked per recipient, so a retry only reaches the recipients still missing. Delivery is at-least-once: a recipient may rarely receive a copy twice, never zero copies while the notification module works. Templates: `llm.budget_warning`, `llm.budget_exhausted` and `llm.budget_oversized` (English and Italian).

## Usage

`GET /v1/admin/llm/usage` groups the finalized calls of a period by model, user or calling module (requests, input and output tokens), and returns the current month's rollup and the budget. `GET /v1/llm/me/usage` gives a user their own month, split by whether the organization or their own linked account paid. The console's **Usage** and **Budget** tabs at `/admin/llm` read these routes. Installation inference calls appear under the model `installation:<name>`; a call made by a background worker for an organization (indexing) has no user, so it is billed to the organization and grouped under an empty user in the by-user report.

## Sign in with ChatGPT

A model configured with `credentialRef.kind = user_account` is paid by the **calling user's own ChatGPT plan** instead of an organization API key. Each user links an account once; the module keeps its sign-in tokens sealed on the server (the browser never sees them) and refreshes them as needed. This is the "Sign in with ChatGPT" program OpenAI documents for open-source and locally hosted applications: OpenID Connect with PKCE and a callback on `127.0.0.1`. Plan usage still counts against the organization's budget.

### Link your ChatGPT account

Users link accounts in their security settings, on the **AI accounts** tab (`/user/security?tab=ai`, shown with `llm.accounts.self`). Which flow they see depends on `siwc_mode`:

- **Local installation (`loopback_local`).** Choose **Link a ChatGPT account**. OpenAI opens in the same window; sign in with the ChatGPT account you want to use and allow plan usage when asked. OpenAI sends the browser back to the installation and the console returns to the tab with the account linked. This works only when the browser runs on the same machine as the API, which must be reached as `http://127.0.0.1:<port>`.
- **Hosted installation (`hosted_paste`).** Choose **Link a ChatGPT account** and then **Open OpenAI**; OpenAI opens in a new tab. Sign in and allow plan usage. OpenAI then tries to open an address starting with `http://127.0.0.1` and the tab shows a connection error: that is expected. Copy the full address from that tab's address bar, paste it into the console and choose **Complete linking**. The address works once and for ten minutes.

OpenAI's overview documents the program for open-source and locally hosted applications and points remotely hosted ones to an interest form, so enabling `hosted_paste` on a hosted installation is the operator's decision, not a default.

A user may link several accounts (for example, different workspaces) and **Select** the one plan-billed models use; the list of models they can use follows the selected account's own catalog. **Unlink** revokes the sign-in at OpenAI (best-effort) and removes the account. Operators see every member's accounts on the **Accounts** tab of `/admin/llm` and can force-unlink one.

### Account states

| State | Meaning | What to do |
|---|---|---|
| Active | The account can pay for calls | — |
| Plan usage not granted | The sign-in is valid but OpenAI did not grant plan usage | Sign in again and allow plan usage |
| Sign-in needed | OpenAI no longer accepts the stored sign-in (it expired, was revoked or was reused) | **Re-authorize**: sign in again to the same account |
| Revoked | Reserved; not set in this version | Unlink and link again |

A sign-in that comes back as a *different* ChatGPT identity than the account being re-authorized is refused and the stored account is left untouched.

### Operator setup

1. Enable **Allow hosted providers** (both modes need it: prompts leave the installation for OpenAI).
2. Choose **Sign in with ChatGPT** in the llm settings. For `loopback_local`, `OPERATOR_API_URL` must be exactly `http://127.0.0.1:<port>` (explicit port, not 80); restart the backend after switching to it, because its callback route is mounted at boot. Outside development the API answers `421 Misdirected Request` to a host it does not serve, so on a production-like installation `CONSOLE_HOST` must be that same `127.0.0.1:<port>` for the callback to arrive; otherwise use `hosted_paste`. The console origin (`OPERATOR_FRONTEND_URL` or the platform frontend URL) must be set too, or the callback cannot send the browser back to the console (a warning is logged at boot). For `hosted_paste`, set `siwc_paste_port` only if the default clashes, and use an `https` `OPERATOR_API_URL` in production-like environments.
3. Create a model with the credential kind `user_account` (provider `openai`, a model ID the plan offers, no embeddings, no temperature or output limit) and grant it to the users who should have it.

### How plan calls differ

- Requests to the plan route carry only what it accepts: no temperature or output limit, no metadata, `user` or `previous_response_id`, no `system` messages (use `instructions`), `store` is always `false` and the answer is always streamed. Embeddings are not available.
- Access tokens are refreshed shortly before they expire. Replicas coordinate through a short Redis lease, so one refresh happens at a time; an unusable refresh token marks the account *Sign-in needed*. A `401` from the plan route triggers one refresh and one retry.
- Quota, eligibility and availability errors from the plan route become the usual `llm.*` codes; a fallback never moves a call from one payer to another. A rejection of the client or grant configuration (`subscription_sharing_route_not_supported`, `chatpass_v2_*`, or `invalid_client` while refreshing) is final: the call answers `llm.provider_unavailable` without trying the next plan-billed model, and it does not open the circuit breaker. After `invalid_client`, the same tokens are not presented again for a minute.
- Rate limits protect the flow: 5 link starts and 10 completions per user, and 20 callbacks per client address, each per 10 minutes.

:::note Not verified against a live account yet
The module has been exercised against test doubles, not a real ChatGPT Plus or Pro account. Whether OpenAI accepts a code exchange that starts from a remotely hosted backend, which the paste flow relies on, is part of that pending check; `siwc_mode` ships as `disabled`.
:::

:::note Known limits of the first version
Redis is needed for the one-shot sign-in state: without it the paste flow answers a server error and the automatic callback returns to the console with `token_exchange_failed`. The automatic callback is unauthenticated by nature: a user could try to have someone on the installation's own host approve a sign-in they started, which would link that person's account to them; OpenAI shows a consent screen and attempts last ten minutes. While OpenAI cannot be reached, plan-billed models disappear from the self list because their catalog cannot be read. A callback refused by the per-address rate limit reports `state_invalid`, although the attempt can be retried after the window. That the automatic callback with `Host: 127.0.0.1:<port>` reaches the operator API (no `421`) is still to be checked live on an installation running `loopback_local`.
:::

## Installation inference endpoints

Search over documents needs embeddings and, optionally, a reranker. Those models run on [text-embeddings-inference](https://github.com/huggingface/text-embeddings-inference) (TEI) servers that the **operator** declares for the whole installation ([ADR-0023](/adrs/core-retrieval-module)); they are served only to the `retrieval` module and are separate from the per-organization credentials and models above.

They are declared in one environment variable, a JSON array:

```bash
RETRIEVAL_INFERENCE_ENDPOINTS=[{"name":"embed","url":"http://tei-embed:80","kind":"embed","boundary":"local","model":"BAAI/bge-m3","revision":"<sha>","pooling":"cls","normalize":true,"truncate":true},{"name":"rerank","url":"http://tei-rerank:80","kind":"rerank","boundary":"local","model":"BAAI/bge-reranker-v2-m3","revision":"<sha>","truncate":true}]
RETRIEVAL_INFERENCE_API_KEY=<shared bearer key; an endpoint may name another variable in "apiKeyEnv">
```

Each endpoint states its `boundary`: `local` (inside your infrastructure) or `hosted` (a third party, which then must use `https` in a production-like environment). The `model` and `revision` must be exactly what the server was started with (`--model-id`, `--revision`).

An endpoint is **verified, not trusted**. Before use, and again at most every minute, the module asks the server which model and revision it is running, and for an embedding endpoint measures the vector size. If the server now runs something else, the call is refused (`ErrLLMProfileMismatch`) rather than mixing vectors of two models (a swap to a model with the same vector size is only detected at the next re-verification, up to one minute later); an unreachable server is `ErrLLMProviderUnavailable`. Each endpoint has an immutable profile ID derived from its model, revision and settings, so moving a model to another host keeps its ID.

A malformed value is a warning in the log, never a boot failure: a bad endpoint is left out, and with the variable unset the module logs nothing. The module never contacts an endpoint while starting.

Calls are billed to the organization they run for, through the same budget and usage ledger as any other call (provider `tei`, model `installation:<name>`). The private-address rule is unchanged for organization endpoints: an `ollama` or `openai_compatible` base URL that resolves to a private address is still refused in a production-like environment, and `tei` cannot be used as an organization provider.

## Data-subject rights

The module registers an `iface.PIIProducer` with the subject `llm`. Export returns explicit projections only — never a credential, an endpoint or an envelope: the grants the user holds, the grants they issued, references to the credentials and models they created, their usage rows (model, purpose, calling module, counters, outcome, dates — the ledger holds no prompts), the budgets that name them as extra recipient or last editor, the budget alerts delivered to them, and their linked ChatGPT accounts (label, email, status and dates; never a token, the client identifier OpenAI issued or the OpenAI subject).

Erasure deletes the grants the user holds; replaces the actor id on the grants they issued, the credentials and models they created and the budgets they last edited with a fixed constant (`erased-subject`) that is not derived from the user; and removes them from every budget's extra recipients and every alert's delivered list. Usage rows depend on the erase mode: a hard delete removes them, an anonymizing erasure keeps the counters with the user replaced by a **random identifier per row** (so the rows cannot be linked to each other into a profile) and the credential reference removed. A row of a call still in flight is anonymized in both modes and removed later by retention. Linked ChatGPT accounts are handled in both erase modes: every account of the user is deleted and the sign-in each deleted account held is revoked at OpenAI (best-effort). Credentials, models and budgets are organization assets and stay. A request with an empty subject id is refused before any query: it would otherwise match every row created without a user.

## Status

Foundations and the gateway are delivered ([ADR-0022](/adrs/core-llm-module)): the catalog, access model, encrypted secrets, data-subject rights, the six provider adapters, routing with fallback and circuit breaking, the usage ledger and monthly budget with alerts, connectivity tests, model discovery and the prompt test, and the `/admin/llm` console page (tabs for models, credentials, usage and budget, kept in the URL). Sign in with ChatGPT for per-user subscriptions (`credentialRef.kind = user_account`) is delivered as well, in both modes, with the live check against a real ChatGPT account (and the decision to enable `hosted_paste` on a hosted installation) still pending; the console shows it as the **AI accounts** tab in security settings and the **Accounts** tab at `/admin/llm`.

Installation-level inference for the `retrieval` module ([ADR-0023](/adrs/core-retrieval-module)) is delivered as the first step of that module: operator-declared TEI embedding and reranking endpoints, verified against the server, with no route and no console page of their own.

:::note Known limitations
TEI's default `--payload-limit` is 2,000,000 bytes, while one embedding request may carry up to 32 inputs of 64 KiB each. An oversized batch is answered with HTTP 413 and surfaces as `ErrLLMInvalidRequest`; the deployment overlay sets `--payload-limit` accordingly.

Editing a model's grants or a budget's extra recipients in the console also needs `system.tenants.admin`, because both pickers list the organization's members through the tenant API. Without it the editor shows a hint instead of the members. The usage report grouped by user shows user IDs, not names.
:::

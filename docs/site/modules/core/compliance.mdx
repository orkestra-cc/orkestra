# compliance

Platform **audit trail** + **GDPR data-subject rights**. Re-homed from a removed addon back into the always-loaded core by [ADR-0009](/adrs/core-compliance-module) — the personal data it acts on (user, auth, tenant) is core-owned, so the compliance plane ships on day one.

## What it owns

- **Audit trail** — an append-only `compliance_audit_events` collection. Every other module emits events through the `iface.AuditSink` seam without importing this package; the sink write is fire-and-forget so it never blocks a hot path.
- **Auth security events** — initialization wires the sink to the canonical auth service through `iface.AuditSinkSetter` under `module.ServiceAuthService`, alongside the existing password-service and tenant-service consumers. Successful initial-password enrollment emits `self_password_added` through the auth security-event lane and mirrors it once as `auth.password.added` in the compliance trail. Enrollment does not also emit a direct password-service audit event; existing password-service direct-audit actions keep their sink.
- **Module-config change events** — every authenticated mutation of a module's configuration (`PATCH /v1/admin/modules/{name}`, `PATCH …/environments/{env}`, `PUT …/active-environment`, enable/disable) emits `module.config.updated`, `module.config.environment_activated`, `module.enabled` or `module.disabled` into the same trail with the acting user's UUID, tenant context, IP, User-Agent, the key **names** the request submitted and the failure code — never values or secrets, never the actor's email. Emission is best-effort (a sink failure is logged, not rolled back) and events share the trail's existing two-year retention; deployments needing guaranteed evidence should plan a durable outbox. The records hold an actor UUID, tenant context, IP and User-Agent for privileged-change forensics — the deployer documents the applicable lawful basis and retention for them in its RoPA / privacy materials.
- **GDPR DSR pipeline** — right-of-access **export** and right-to-erasure over the `iface.PIIProducer` seam. The pipeline walks every registered producer (`user`, `auth`, `tenant`, `authz`, `notification`, `llm`, `retrieval`) at request time, so adding a producer needs no change here. Export bundles are keyed by producer key — `auth.operator` and `auth.client` for the two auth tiers — since bundle version `2`.
- **Per-tenant KMS** — envelope encryption + crypto-shred of a tenant's data-encryption key.
- **Legal hold** — an active hold on a subject blocks erasure platform-wide (DSR erase + retention auto-cleanup return `409`).
- **Legal hold review, expiry and notes** — a hold can carry a `reviewAt` date (it only flags `reviewDue` in the console, it never releases) and an `expiresAt` date (must be in the future). A hold stops blocking erasure the instant its expiry passes, in the DSR gate, the published checker and the preview alike, even before the job `compliance.legal_hold_expiry` (hourly) records the release as `system:expiry`; two replicas release each hold once. Operators add append-only notes (1 to 1000 characters, personal data masked). A release needs a reason (1 to 500 characters, `compliance.reason_required`). Placing, updating, noting, releasing and expiring a hold are audited (`compliance.legal_hold.*`; the note text is never copied to the audit event).
- **Minimum retention on hard delete** — a hard delete (operator execute, self-service erase, the retry of an incomplete request, retention auto-cleanup) is refused until the subject's retention floor has passed: the platform floor (`min_retention_years` after the account was created; `0`, the default, turns it off) and any longer obligation a module reports for the subject. The refusal is `409` `compliance.retention_minimum_not_met` with `retainUntil` and `reasons`; nothing is recorded and no module runs, and a request stays pending. If the check itself cannot be completed the hard delete is refused with `503` `compliance.retention_check_unavailable`. Anonymize is never held back. A legal hold is checked first and answers `409` `compliance.legal_hold_active`. An incomplete request that is still inside the floor on retry stays incomplete with last error `retention_minimum`.
- **Retention auto-cleanup** — a daily job that hard-deletes anonymized user tombstones past the retention window. **Off by default.**
- **Admin-opened requests and approvals** — an operator can open an erasure request for a subject (`POST …/compliance/erasure-requests` with `userUuid`, a mandatory `reason` and the `mode`). The opener's approval is recorded with the reason and the request is locked to that mode; the subject cannot open, approve or execute their own request. Opening is refused with `409` when the subject is under a legal hold (`compliance.legal_hold_active`), already has a pending or incomplete request (`compliance.erasure_request_exists`, with the existing `requestId`) or, for a hard delete, is inside a minimum retention (`compliance.retention_minimum_not_met`). `erasure_required_approvals` (1–5, default `1`) sets how many distinct operators must approve before a pending request runs; it is read when the request is created and stored on it, and a request without it needs one. Operators approve with `POST …/erasure-requests/{id}/approve` (`mode`, mandatory `note`); the first approval locks the mode, a second approval by the same operator is `compliance.erasure_already_approved` and a different mode `compliance.erasure_mode_mismatch`. Executing counts the executor as an approver: with fewer distinct approvals the answer is `409` `compliance.erasure_approvals_missing` with `have` and `need`, and nothing is written. The execute `mode` is optional: left out, the request runs in the mode its approvals locked (hard delete when none), so an anonymize request is never held back by the hard-delete retention gate; a different mode is refused with `compliance.erasure_mode_mismatch`. Retrying an incomplete request needs no approvals.
- **Erasure receipt and request history** — `GET …/compliance/erasure-requests` takes `status` (`open`, the default: pending and incomplete with `closable`, all of them as before; `completed`, `rejected`, `closed_partial`, `all`), `userUuid`, `limit` (1–200, default 50 for the closed statuses) and `after`, and answers `{items, next}`; `next` is an opaque cursor that pages exactly even when requests share a timestamp. `GET …/erasure-requests/{id}/receipt` returns the receipt of a `completed` or `closed_partial` request, built from the request row (which is kept): subject and operator UUIDs, source, mode, approvals with their masked notes, who executed and when it finished, attempts, each producer's outcome and row counts, the totals, the abandoned producers and the close note. A pending, incomplete or rejected request answers `409` `compliance.erasure_receipt_unavailable`. When a request completes or is closed partially, the audit event `gdpr.dsr.erasure_receipt` records the same receipt without notes (UUIDs, counts and producer keys), once per closure. Audit events expire (flat TTL); the request row does not, so the receipt can be downloaded again later.
- **Mediated erasure-request workflow** — a subject lodges a request; an operator reviews, then executes or rejects it. Every erasure path (this one, self-service erase and retention) records a request before any producer runs — except for a subject already under a legal hold, for whom nothing is recorded — and a request is `completed` only when every producer has finished. Otherwise it stays `incomplete`: the platform retries the producers still pending or failed with growing backoff (up to 20 attempts), keeps the counts already erased, and then waits for an operator, who can retry it. An attempt is counted when a run claims the request, so a run that dies before recording its outcome still uses one, and a producer that crashes (panics) is recorded as failed while the other producers still run. Every installed producer is recorded on the request as pending before the first one runs, so a run that dies midway still names every producer that held the subject's data: if one of them is uninstalled before it finishes, the request stays `incomplete` and can only be closed as `closed_partial`, never `completed`. Recording a run's outcome is bounded by the run's lease; if it cannot be recorded, the request is reported as `incomplete` and retried. When several replicas run retention at once, a subject still gets a single retention request. The console shows why the last run did not finish (blocked by a legal hold, or failed), refreshes the list every 30 seconds while an automatic retry is scheduled, and tells the operator when another run already holds the request. A request whose remaining producers are no longer installed can be closed with a mandatory note as `closed_partial`, which records the abandoned producers and is audited. A producer installed since the request last ran has not erased the subject's data yet, so it keeps the request open, and a close that races a retry is refused rather than overwriting it. A request that has started cannot be rejected. Erasures never complete while the subject is under a legal hold.
- **SOC2 evidence** — a point-in-time controls snapshot. **Gated off by default** (`soc2_enabled`).
- **Compliance policies** — a named, versioned catalog: one platform policy plus tenant policies assigned to internal or client tenants. A policy sets what reaches the operational logs and traces (IP addresses, user agents, user identifiers, personal-data keys, free-text scanning) and the audit retention of each [retention class](#retention-classes) — stored and resolved today, applied to stored audit events by a later stage. Changes need a reason, keep an immutable version, and — when they lower protection — wait for a second operator (four eyes).

## Routes

- **Self-service** (authenticated subject): `POST /v1/me/dsr/{export,erase,erasure-request}`.
- **Admin reads** (`system.compliance.audit.read`): `GET /v1/admin/audit-events`, `…/compliance/legal-holds` (`?userUuid=&includeReleased=`), `…/compliance/retention/preview`, `…/compliance/erasure-requests` (filtered by status, paged) with its `…/{id}/receipt`, and `…/compliance/soc2` (when enabled).
- **Admin writes** (step-up gated): place, change (`PATCH …/legal-holds/{id}`: `reviewAt`, `expiresAt`, `clearReviewAt`, `clearExpiresAt`), annotate (`POST …/legal-holds/{id}/notes`) or release legal holds (`system.compliance.legalhold.manage`), open, approve, execute, reject or close erasure requests (`system.compliance.dsr.manage`). The role table grants this key by suffix, so the platform `manager` role holds it today, as for the other `.manage` keys.
- **Policy engine reads** (`system.compliance.policy.read`): list and read policies and their versions, the effective policy of a tenant, the retention-class catalog, assignments, change requests, and validation previews (`POST …/compliance/policies/validate`, `POST …/compliance/policy-assignments/{tenantId}/validate`).
- **Policy engine writes** (`system.compliance.policy.manage`, step-up gated): create, change and delete policies, assign a policy to a tenant or move it back to the platform policy, approve or reject change requests. A change that waits for four eyes answers `202` with the created request.

  Until `CEDAR_ENFORCE_ACTIONS` includes `system.compliance.policy.manage`, the role table grants it by suffix to the platform `manager` role too, who can then manage **and approve** policies — the same as `legalhold.manage` and `dsr.manage` today. Add it to `CEDAR_ENFORCE_ACTIONS` once the policy engine is in use.
- **Client surface** (Tier 2, own tenant only): `GET /v1/tenants/{tenantId}/compliance/policy` shows a client how its own data is logged and the retention configured for it; `retentionEnforced` stays `false` until audit events are stamped and deleted by class.

## Config

`soc2_enabled` (default `false`) · `auto_cleanup_enabled` (default `false`) · `retention_years` (default `5`) · `export_retention_days` (default `30`) · `min_retention_years` (default `0`, 0–30) · `erasure_required_approvals` (default `1`, 1–5) · `four_eyes_enabled` (default `true`).

:::note Always-on
Unlike a fork's optional modules, the audit log + GDPR DSR pipeline cannot be disabled — that is the point of making compliance core. Only the SOC2-evidence and retention-auto-cleanup sub-features are gated.
:::

## Retention classes

| Class | Events | Purpose | Legal basis | Minimum | Default | Set per tenant |
|---|---|---|---|---|---|---|
| `admin_access` | Tier-1 operator logins, logouts, failed logins, MFA, impersonation | Control of administrator access | Art. 6(1)(c) GDPR — Garante, system administrators measure | **184 days (hard)** | 365 | yes |
| `privileged_change` | Configuration, role, user, tenant and policy changes by operators | Accountability and security | Art. 6(1)(f) — legitimate interest | 1 | 730 | yes |
| `client_activity` | Actions and logins of Tier-2 client users | Security of the service to the client | Art. 6(1)(b) or (f) | 1 | 365 | yes |
| `authentication_security` | Authentication security events | Fraud and abuse detection | Art. 6(1)(f) | 1 | 365 | no |
| `compliance_evidence` | Policy versions, assignments, change requests, DSR, legal holds, verifications | Demonstrating compliance (art. 5(2), 30) | Art. 6(1)(c) | 1 | 1825 | no |

The catalog is fixed in code: a policy only chooses the days, within the minimum and ten years. Adapt the purposes and legal bases to your own records of processing. Stamping and deleting audit events by class is a later stage; until it ships, audit events keep the collection's current retention.

## Four eyes

With `four_eyes_enabled` on (the default), a policy change that raises warnings is not applied: it becomes a change request that another operator approves or rejects with a note. The warnings are:

| Warning | Raised when |
|---|---|
| `less_restrictive_than_platform` | a tenant policy is less restrictive than the platform policy |
| `less_restrictive_than_current` | an assignment, a reassignment, a removal or an edit leaves a tenant with a less restrictive effective policy than it has now |
| `retention_longer_than_default` | a class is set above its default |
| `retention_shorter_than_default` | a class is set below its default, so audit evidence expires sooner |
| `sink_retention_longer_than_default` | a sink value of the platform policy is above its default |
| `external_sink_changed` | an external sink is added or changed against the current platform policy (GDPR art. 28 and 44 — check the processor agreement and transfer basis) |
| `ip_full` | full IP addresses are kept |
| `review_overdue` | the review date is in the past or empty |
| `accountability_incomplete` | the record-of-processing or assessment reference is empty |

The operator ticks an acknowledgement to send a change with warnings. An approval re-checks the current state and supersedes the request if the policy or the assignment changed meanwhile. Requests expire after 14 days: a request past that age can no longer be approved or rejected, even before the hourly sweep marks it. Reasons and notes are personal data kept as compliance evidence: e-mail addresses, IBANs and codici fiscali typed into them are masked before they are stored.

:::caution Supported controls, not conformity
The policy engine supports GDPR minimisation and storage limitation and ISO/IEC 27001 controls such as A.5.3, A.8.11 and A.8.15. Conformity is shown by your risk assessment and Statement of Applicability, not by this module.
:::

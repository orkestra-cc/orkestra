# `compliance` — audit trail + GDPR data-subject rights (core module)

Core module (ADR-0009). Always-on. Owns the platform **audit trail**, the **GDPR DSR pipeline** (right-of-access export + right-to-erasure), **per-tenant KMS** crypto-shred, **legal hold**, **retention auto-cleanup**, the mediated **erasure-request workflow**, and (gated off by default) **SOC2 evidence**, plus the **compliance policy engine** (named, versioned policies that drive log/trace masking and set the per-class audit retention that a later stage (T4) applies to stored events, with four-eyes changes).

Re-homed from the ADR-0006-removed `internal/addons/compliance` addon; see [ADR-0009](../../../../docs/adr/0009-core-compliance-module.md) + [plan](../../../../docs/plans/compliance-module.md).

## Key contracts & invariants

- **DSR reuses the existing `iface.PIIProducer` seam — do NOT add a parallel one.** Producers register themselves with the `PIIProducerRegistry` (created in `cmd/server/main.go` before `InitAll`) during their own `Init`. Live producers: `compliance.dsr_exports` (this module), `user`, `auth` (two instances keyed `auth.operator` / `auth.client`), `tenant`, `authz`, `notification`, `llm`, `retrieval` (reports `Pending` until its index erasure is finalized: about one fencing window, 16 minutes, after the first pass, so a request typically completes on its ~6th automatic run, ~30 minutes; with no retrieval overlay it is never pending). Export bundles are keyed by producer key (bundle metadata version `2`), not by `Subject()`. `DSRService` walks `registry.List()` at request time, so producer registration order/timing doesn't matter.
- **Erasure lifecycle (ADR-0023 D12, amends ADR-0009).** Every erasure path (operator execute, self-service `POST /v1/me/dsr/erase`, retention) writes its `compliance_erasure_requests` row (`source` `request | self_service | retention`) as `incomplete` and leased before any producer runs, so a crash leaves a row the worker finishes — unless the subject is already under a legal hold: then nothing is written (a lodged request stays `pending`, self-service and retention record nothing). Each producer instance has a key: `PIIProducerKeyer.ProducerKey()` when non-empty, else `Subject()`; the second and later duplicates get `#2`, `#3` in registration order (`producerKeys`, shared by erase and export); `metadata` is reserved for the export bundle, so a producer keyed or subjected `metadata` gets a suffix too. A suffixed key depends on registration order, so the first time one is generated a WARN asks the producer to implement `iface.PIIProducerKeyer`. Per-key outcome is `done | pending | failed`; only all-`done` completes the request (`completed`). **Every registered producer is on the row as `pending` before any producer runs** (`DSRService.PlanProgress`): `EraseNow` inserts the row with them, and `run` stores, under the lease (`RecordProgress`, fenced like `Settle`, keeps the lease), any registered key the stored progress lacks — the first execution of a lodged request, or a producer first seen on a later run. When that write fails no producer runs, the error is returned and the row stays `incomplete` for the worker. So a run that dies before `Settle` still names every producer that held the subject's data, and a producer unregistered afterwards leaves the request `incomplete` (closable as `closed_partial`), never `completed`. A producer that panics (erase or export) is recovered: it is logged at ERROR (subject, key, userUuid, panic, stack) and recorded as `failed` with the fixed error `producer panicked`; the other producers still run, so one broken producer cannot crash the replicas running the worker. The partial counts of a failed producer are kept and accumulate across retries. A run holds a 5m lease (BSON-truncated to the millisecond) with a deadline of half the lease; repository `Claim` also sets `nextAttemptAt` to the claimed lease, so a run started by an operator Execute that dies is re-run by the worker once the lease expires. **Attempts are counted when a run claims the request**, not when it settles: `Claim` sets `attempts: 1` (fresh budget), `EraseNow` inserts attempt 1, `ClaimDue` increments it and never claims a row that already used 20; `run` uses `row.Attempts` as its number. So a run that dies before Settle still spends its attempt and a request that never settles stops after 20 claims. `Settle` is fenced by the lease **and** `status: incomplete`, and runs on a context bounded by what is left of the lease (at least 5s); when it fails or the lease was lost the run logs WARN and reports the request as stored (`incomplete`), never the state it meant to write. The worker ticks every 1m (50 requests per pass); backoff is `1m << (attempts-1)` capped at 6h, at most 20 attempts. Exhaustion clears `nextAttemptAt` on the settle of the 20th run (a 20th run that never settles leaves a past `nextAttemptAt`, which `ClaimDue` ignores) and leaves the row `incomplete` (never completed) until an operator retries it: Execute on an incomplete request reuses the stored mode and resets attempts. A hold placed after the start runs no producer, records `lastError: legal_hold_active` and counts as an attempt (`run_failed` for other run errors). Producer error text is logged (WARN), never stored on the row, which is retained evidence. A progress key whose producer is no longer registered keeps the request `incomplete` until an operator closes it with `POST …/erasure-requests/{id}/close`: allowed only when every not-done producer is unregistered, judged on `PlanProgress(progress)` so a producer registered since the last run (it never erased the subject's data) counts as pending and blocks it (else 409 `compliance.erasure_request_not_closable`; `ListOpen`'s `closable` uses the same rule); the write is fenced by the exact progress that was checked, so a run that changed it meanwhile makes the close fail as 409 `compliance.erasure_request_busy` instead of overwriting it, note mandatory and masked (an empty note is refused by request validation with 422, a blank one with 422 `compliance.erasure_close_note_required`), status `closed_partial`, the `abandoned` keys on the row, the expired lease removed (so a dead run's late Settle cannot reopen it), audit `gdpr.dsr.erasure_closed_partial`. Reject on an incomplete request is 409 `compliance.erasure_request_started`; a request held by another run is 409 `compliance.erasure_request_busy`. **`PurgePersonalData` must be idempotent**: compliance calls it again on retry.
- **EraseMode (`iface.EraseMode`)**: `EraseAnonymize` keeps the user identity row (UUID survives, email aliased, profile blanked — the tombstone retention later reaps); `EraseHardDelete` removes it. Satellite producers (auth/tenant/authz/notification) delete in **both** modes (their rows are pure user linkage — no anonymizable residue).
- **Audit is fire-and-forget + nil-safe.** `sink.Emit` never returns an error and writes on a detached context so a cancelled request can't abort the insert. Other core modules consume the sink via `SetAuditSink` and nil-check it; this module provides it.
- **Erasure receipt and request history.** `repository.List(ErasureListFilter{Statuses, UserUUID, Limit, After})` orders `requestedAt desc, uuid desc` (index declared in `Collections()`), fetches `Limit+1` to know whether a page follows and returns the opaque cursor (base64url of `requestedAtMs|uuid`, ms because BSON dates are) of the last item; `Limit 0` is unlimited with no cursor (what `open` without `limit` uses, as before); a bad cursor is `ErrErasureCursorInvalid` → 422 `compliance.invalid_cursor`. The handler's `status == open` (or omitted) is the explicit unlimited-without-`limit` case. The receipt audit's actor is the completing operator; for a request the retry worker completed it is `system:erasure-retry` with actor type `system` (the receipt's `executedBy` stays the row's `resolvedBy`); if the `ClosePartial` re-read fails after the write, the receipt is still audited from the row in hand. `erasuretest.MemRepo.List` mirrors it. `BuildErasureReceipt(row, now)` exists only for `completed` and `closed_partial` (`ErrErasureReceiptUnavailable` → 409 `compliance.erasure_receipt_unavailable`); `executedBy` is the row's `resolvedBy` (Claim / EraseNow / ClosePartial), the close note is `resolutionNote` (already masked), producers keep progress order. The audit event `gdpr.dsr.erasure_receipt` (metadata = receipt minus notes: UUIDs, counts, keys) is emitted in `run` only after a settle that landed as `completed` (never on a failed settle or lost lease) and in `ClosePartial` after its write, so exactly once per closure.
- **Retrieval shares the audit sink.** `publishAuditSink` pushes the sink into `module.ServiceRetrieval` through `iface.AuditSinkSetter` (the same push as `llm`), so retrieval's erasure events reach the compliance trail. An absent retrieval service is skipped.
- **Canonical auth security events share the audit sink.** `Init` resolves `iface.AuditSinkSetter` under `module.ServiceAuthService` and wires the sink once, alongside the existing password-service and tenant-service consumers. Auth maps `self_password_added` to `auth.password.added` (`models.ActionAuthPasswordAdded`): a successful initial-password enrollment writes one auth security event and mirrors it once into `compliance_audit_events`. Enrollment must not also directly emit from `PasswordAuthService`, or the compliance row would be duplicated. Existing password-service direct-audit actions retain their sink wiring.
- **Legal hold blocks erasure platform-wide.** `DSRService.Erase` (and therefore retention + the workflow's execute) returns `ErrLegalHoldActive` → `409` when any active hold exists for the subject.
- **Minimum-retention gate (hard delete only).** `DSRService.CheckRetention` (nil for `EraseAnonymize` or with no gate wired) consults `RetentionGate.Evaluate`: the platform floor — `createdAt` of the subject's row in `operator_users`/`client_users` plus `min_retention_years` (read fresh; `0` = off; no user row = no floor), reason `platform_minimum` — and every registered producer implementing `iface.PIIRetentionReporter`; the binding obligation is the latest `Until` still in the future, with all reasons. Order: Execute (pending or incomplete, on the effective mode — stored mode for an incomplete one) status → legal hold → retention → claim; EraseNow legal hold → retention → insert (so a refused hard delete records no row and runs no producer); `EraseRemaining` (retry) legal hold then retention, a refusal settling the row incomplete with `lastError: retention_minimum`, attempt counted, normal backoff. The reaper treats a gated subject like a held one (skipped, nothing recorded). A reporter error, panic or lookup failure fails closed: `ErrRetentionCheckUnavailable` → 503 `compliance.retention_check_unavailable` (never 409). Refusal = `*RetentionGateError` (`errors.Is` `ErrRetentionMinimum`) → 409 `compliance.retention_minimum_not_met` whose body carries `retainUntil` (RFC 3339) and `reasons` through `errcode.Error.WithExtension` (extra top-level body members; the envelope members cannot be overridden). `ErrLegalHoldActive` mappings now carry `compliance.legal_hold_active`. Handlers share `erasureGateError`.
- **Admin-opened requests and N-of-M approvals.** `Open` (source `admin`; `requestedBy`, `mode`, the opener's `approvals[0]` with the masked reason as note) refuses in order: reason (`ErrReasonRequired`, 422 `compliance.reason_required`), the opener being the subject (`ErrErasureSelfApproval`), legal hold, retention (hard delete only; anonymize is never gated), then `HasOpen` (`*ErasureRequestExistsError` → 409 `compliance.erasure_request_exists`, body member `requestId`). `HasOpen` is the pre-check; the race between two simultaneous opens is closed by a partial unique index on `(userUuid, source)` scoped to `models.PendingAdminErasurePartialFilter` (pending admin-opened requests; ordered `$and` of single-key maps): the loser's insert fails with `repository.ErrErasureOpenExists` and `Open` re-reads the winner's uuid into `*ErasureRequestExistsError`. A successful `Open` is audited as `gdpr.dsr.erasure_opened` (subject UUID, mode, `requiredApprovals`). `Lodge` and `Open` snapshot `requiredApprovals` from `ErasureRequestService.SetRequiredApprovals` (config `erasure_required_approvals`, clamped 1–5; a missing value on a row counts as 1). `Approve` (pending only; actor ≠ subject; masked note required) calls `repository.AddApproval`, a single compare-and-set (pending, `approvals.by` ≠ actor, mode absent or equal) that `$push`es the operator's element and sets the mode, so two operators approving at once both land and neither can duplicate; a lost CAS (`ErrErasureApprovalConflict`) is resolved by re-reading the row into `ErrErasureAlreadyApproved` / `ErrErasureModeMismatch` / not found. `Execute` of a **pending** request: the execute body `mode` is optional (`ExecuteInMode`): empty means the mode the approvals locked, else hard_delete (legacy rows); a different one is `ErrErasureModeMismatch`, judged before the retention gate so the gate sees the mode that will run. Order: status → hold → mode → retention → actor ≠ subject, `distinct(approvals ∪ {actor}) ≥ max(1, requiredApprovals)` else `*ErasureApprovalsMissingError{Have, Need}` (409 `compliance.erasure_approvals_missing`, `have`/`need` members) with nothing written; the executor's approval (note `executed`, skipped when already an approver) goes into the same `Claim` update, which keeps the lease and attempt fences and adds fences on the mode and on `approvals.by`. Two operators executing at once: the lease/status fence lets one run, the other gets not found. A same-operator approval landing between the read and the Claim makes the Claim retry once without adding an approval. Incomplete requests (retries, worker) skip approvals. Approvals carry operator UUIDs and masked notes only; `gdpr.dsr.erasure_approved` is audited with UUIDs and counts. `dsr.manage` reaches the platform `manager` role by suffix (as `legalhold.manage` does); no new permission keys.
- **Legal hold has a review date, an expiry and notes.** A hold counts only while `active && (expiresAt absent || expiresAt > now)`: one `heldFilter` serves `IsHeld` and `ListActive` (so the DSR gate and the preview agree), and an expired hold stops blocking at its instant even if the job has not run. `ExpireDue` (job `compliance.legal_hold_expiry`, hourly, `Jobs()` on the module) releases per hold with a `FindOneAndUpdate` CAS on `active:true` + `expiresAt <= now` (bounded batch of 500) and audits `expired` only for the holds this call released, so two replicas act once; `releasedBy` is `system:expiry`. `reviewAt` only drives `reviewDue`; `expiresAt` must be in the future on place/update (`compliance.legal_hold_expiry_past`, 422). Release needs a reason and notes are 1-1000 characters, both `NormalizeReason`-style trimmed and masked (`compliance.reason_required`); note text never goes to audit metadata. Update/notes only touch holds in force (`heldFilter` + uuid): a lapsed hold (active in the row, past expiry) answers 404 and cannot be revived, but `Release` (active:true only) still works on it. List rows carry `expired` (lapsed, unreleased; `reviewDue` is false then). Index `(active, expiresAt)` serves `ExpireDue`.
- **Retention is OFF by default** (`auto_cleanup_enabled=false`) and reads config fresh each run. The ticker is launched by `Start()` but `RunOnce` no-ops while disabled. It hard-erases through the DSR, so the legal-hold gate applies. **Every replica runs it**, so `HasIncomplete` then `EraseNow` is not atomic on its own: a partial unique index on `userUuid` (`models.ActiveRetentionErasurePartialFilter`: `$and: [{status: incomplete}, {source: retention}]` — an ordered `$and` of single-key maps, never one two-key map, so the spec marshals identically on every boot) admits one incomplete retention request per subject; the second replica's insert fails with `repository.ErrErasureRequestActive` before any producer runs and `RunOnce` skips the subject (the winning request, then the retry worker, owns it). Requests of other sources are not constrained by it.
- **SOC2 is gated** behind `compliance.soc2_enabled` (default false) — but **at request time, not boot time**, so the toggle works without a restart. The handler + route (`GET /v1/admin/compliance/soc2/evidence`) are mounted unconditionally; the handler 404s when the flag is off (`SOC2Handler.enabled` closure, read live via `deps.GetConfigBool`). The `SOC2 Evidence` nav item is emitted unconditionally with `NavItemSpec.RequiresConfig: "soc2_enabled"` and hidden by the navigation filter when off — **don't** gate it inside `NavItems()` on an Init-set bool: `NavItems()` is collected before `Init` runs, so the flag is always false there. Audit + DSR are ungated.
- **Cross-module collection names are inlined as string constants** (`operator_users`, `client_users`, `operator_mfa_factors`) in `services/soc2.go` and `services/retention.go` — compliance must NOT import other modules' packages. Keep these in lock-step with the owning module if it renames a collection.
- **`LocalKMS.CreateKey` is idempotent under concurrency, not just for sequential callers.** Two racing calls for the same tenantUUID both converge on the single winning keyID: `repository.KMSKeyRepository.Insert` translates the unique `tenantUuid` index's duplicate-key rejection into the exported `ErrKMSKeyExists` sentinel, and `CreateKey` rereads the winning row via `GetByTenant` rather than surfacing the raw error. This is load-bearing for a resumable setup saga that may replay the key-creation stage after a crash or a lost response — a second DEK for one tenant would orphan the ciphertexts wrapped with the first on crypto-shred (they'd never be shredded, since `DeleteKey` only ever targets the one keyID the tenant row remembers).
- **`//tenantscope:allow` on DSR-by-user queries**: erasure/export/legal-hold/retention scan by data-subject and are deliberately cross-tenant (a hold blocks erasure platform-wide; retention scans all tenants). Each such query is annotated.
- **Module-config mutations are audited by the SDK admin handler, not by this module.** `pkg/sdk/module.ModuleAdminHandler` emits one event per actual mutation result through `SetAuditSink`/`SetActorResolver` (wired in `cmd/server/admin_wiring.go`): `module.config.updated` (`PATCH /v1/admin/modules/{name}` and `…/environments/{env}`, `Metadata.env`), `module.config.environment_activated` (`PUT …/active-environment`), `module.enabled` / `module.disabled` (the `enabled` half of a PATCH — a separate event from the config half, each with its own outcome). `ResourceType: "module"`, `ResourceID: <name>`, `Outcome` uses the existing `success`/`failure` vocabulary. **Metadata carries key NAMES only** (`keys`, `secretKeys` — the key names the request submitted, so a re-sent unchanged value is listed; schema-derived, sorted, ≤ 64; record-list element keys collapsed to their schema item names; unknown request keys only as `unknownKeyCount`), the stable `code` on failure (validation codes, `module.config_revision_stale`) and `requestId` — never a value, never a secret. The actor is `ActorUserID` + tenant context + IP + User-Agent; **`ActorEmail` is deliberately empty** (the UUID is the attribution; email is mutable PII). Persistence is **best-effort** under this sink's contract — `Emit` returns nothing, may add its bounded 2 s insert latency, and a failed insert is a structured WARN naming `action`/`resourceType`/`resourceId`/`outcome` (never the payload), not a rolled-back config change. This is not complete SOC2 evidence; guaranteed evidence needs the durable-outbox follow-up in the password-login-toggle spec §8. The events reuse `compliance_audit_events` and its existing two-year TTL; actor UUID, tenant context, IP and User-Agent are retained only for privileged-change forensics. **Deployers remain responsible for documenting the lawful basis and retention of these records in their RoPA/privacy materials** — the module records them, it does not decide the legal basis.
- **Policy engine (compliance spec §1–§2, T2).** Exactly one policy is the platform policy (partial unique index; never deleted nor assigned); every other policy is a tenant policy carrying only the tenant-settable classes (`admin_access`, `privileged_change`, `client_activity`) and no `sinks`. `PolicyService` resolves from an immutable snapshot refreshed every 5 s (and at once after a write on the writing replica): assigned policy → platform policy; `""` and assignments to a missing policy → the strictest content in force; before the first snapshot → static platform defaults; a failed refresh keeps the last snapshot (warn at most once a minute). `orkestra_compliance_policy_snapshot_age_seconds` reports the time since the snapshot was loaded and, while no snapshot has ever loaded, the time since start — so the stale alarm can fire on a boot with Mongo down. `main.go` swaps the service into `utils.SwapLogPolicyResolver` and `telemetry.SwapSpanPolicyResolver` after `InitAll`. `*LogContentPolicy` pointers are stable per `(uuid, version)` — the PolicyHandler caches derived loggers by pointer. **Retention is stored and resolved (`RetentionFor`), not yet enforced:** no audit event is stamped or deleted by class until T4, so the Tier-2 summary reports `retentionEnforced: false` next to the configured days.
- **Every policy or assignment write is one Mongo transaction** (a new change request is a single-document insert) with its immutable version (`compliance_policy_versions`) or history row (`compliance_policy_assignment_history`); a reason (1–500 chars) is mandatory and is scanned for e-mails, IBANs and codici fiscali before it is stored (IPs kept, as in the evidence core). The audit event (`compliance.policy.*`, `compliance.change_request.*`, before/after values) follows the commit through the best-effort `AuditSink` until the T3 outbox makes it atomic.
- **Four eyes** (`four_eyes_enabled`, default on): a change whose validation has warnings needs `acknowledgeWarnings` and becomes a pending `PolicyChangeRequest`. The warning codes are `less_restrictive_than_platform`, `less_restrictive_than_current`, `retention_longer_than_default`, `retention_shorter_than_default` (a class below its default: audit evidence would expire sooner), `sink_retention_longer_than_default` (a spec §5.1 sink value above its default), `external_sink_changed` (an external sink added or changed against the current platform policy — GDPR art. 28/44; `PolicyCheck.Current` carries the policy being edited for it), `ip_full`, `review_overdue` and `accountability_incomplete`. Only another operator with `policy.manage` approves or rejects a request (note mandatory); approval re-validates against the current state and marks the request `superseded` (409) when the policy version or the tenant's assignment moved; the pending→decided compare-and-set makes concurrent approvals apply once. Pending requests expire after 14 days (hourly job on every replica, idempotent); an approve or reject that reaches a request past its 14 days before the sweep expires it on the spot (same compare-and-set, audited once by the winner) and answers `change_request_not_pending`. Unassigning a tenant that is gone from the tenant lookup (soft-deleted or purged) but still has an assignment removes it at once without warnings, so its policy does not stay `policy_in_use` forever; a missing tenant without an assignment is still 404. Moving a tenant to a less protective policy — including back to the platform — raises `less_restrictive_than_current`.
- **OpenAPI schema names come from Go type names:** keep policy-engine DTO names specific (the validation issue is `services.PolicyIssue`, not `Issue`); a duplicate name panics the OpenAPI dump at boot. An addon already declares an `Issue`.
- **Personal data in the policy engine.** Operator UUIDs (`createdBy`, `updatedBy`, `requestedBy`, `decidedBy`, `accountability.owner`) and reasons are personal data kept as compliance evidence (class `compliance_evidence`); they are exempt from erasure under GDPR art. 17(3)(b) and (e). Their right of access (art. 15) is not wired into the DSR export yet (open point of the T2 plan). The policy engine supports GDPR minimisation and storage limitation controls; it does not by itself demonstrate conformity.

## Permissions

- `system.compliance.audit.read` — audit list + DSR/legal-hold/retention/erasure-request reads.
- `system.compliance.legalhold.manage` — place/release holds (+ step-up).
- `system.compliance.dsr.manage` — open/approve/execute/reject/close erasure requests (+ step-up). Reaches the platform `manager` role by suffix, as `legalhold.manage` does.
- `system.compliance.policy.read` — policy catalog, versions, effective policy, validation previews, assignments, change requests.
- `system.compliance.policy.manage` — create/change/delete/assign policies and decide change requests (+ step-up). Named in `tenant_scope.cedar` as operator-only (vetoed against `external` tenants).

**Suffix grants are wider than spec §7.** The authz role table grants by suffix, so the platform `manager` role (everything but `.delete`/`.admin`) also holds `policy.manage` — and `.read` reaches `manager`, `operator` and `guest`. The Cedar forbid `system_actions.require_platform_role` that would refuse them runs in shadow mode (it logs, it does not deny). Until `CEDAR_ENFORCE_ACTIONS` includes `system.compliance.policy.manage`, a `manager` can manage **and approve** policies, the same as `legalhold.manage`/`dsr.manage` today. Recommendation: add it to `CEDAR_ENFORCE_ACTIONS` (recommended list in [`authz/AGENTS.md`](../authz/AGENTS.md)) once the policy engine is in use.

All five are `System: true`. `audit.read` and `policy.read` are Cedar-covered by the `read` suffix clause; the three `.manage` keys are named as operator-only tier-aware forbids in [`authz/cedar/policies/tenant_scope.cedar`](../authz/cedar/policies/tenant_scope.cedar) (vetoed against `external` tenants) — that literal is also what satisfies the `policycoverage` CI gate. A new `system.compliance.*` permission with an uncovered suffix must add its own Cedar reference there or CI fails with `permission.cedar.unreferenced`.

## Config (`ConfigSchema`)

`soc2_enabled` (bool, false) · `auto_cleanup_enabled` (bool, false) · `retention_years` (int, 5) · `export_retention_days` (int, 30) · `min_retention_years` (int, 0, max 30; gate above) · `erasure_required_approvals` (int, 1, 1–5; read at creation, snapshotted on the request) · `four_eyes_enabled` (bool, `true`).

`ConfigGroups()` puts these on the full-page rail as three groups: `soc2` ("SOC2 evidence", just `soc2_enabled`), `retention` ("Retention & DSR", `auto_cleanup_enabled`, `retention_years`, `export_retention_days`, `min_retention_years`, `erasure_required_approvals`) and `policy` ("Policy engine", just `four_eyes_enabled`). `retention_years` carries `DependsOn: auto_cleanup_enabled in [true]` — it only matters once the reaper is on, so it stays hidden until then (4 → 3 visible fields at the default).

**`export_retention_days` is deliberately NOT gated on `auto_cleanup_enabled`.** It governs the download TTL of a stored DSR export — the always-on right-of-access pipeline; that TTL is independent of the retention cleanup job, so hiding it behind the cleanup toggle would make an always-relevant setting invisible on a fresh install where auto-cleanup is off. Do not "tidy up" the two `retention` fields into a single `DependsOn` block. `config_groups_test.go` plus this note are the guard rail against that regression.

## Routes

- Self-service: `POST /v1/me/dsr/{export,erase,erasure-request}`.
- Admin reads (audit.read): `GET /v1/admin/audit-events`, `…/compliance/legal-holds` (`?userUuid=&includeReleased=`), `…/compliance/retention/preview`, `…/compliance/erasure-requests` (`?status=open|completed|rejected|closed_partial|all&userUuid=&limit=&after=`, `{items, next}`; `open`, the default, is pending + incomplete with `closable`, unpaged unless `limit` is given) and `…/erasure-requests/{id}/receipt`; SOC2 `GET …/compliance/soc2/evidence` (always mounted; 404 when `soc2_enabled` is off).
- Stored exports: `GET /v1/admin/compliance/dsr/exports?userUuid=` (audit.read, required query); `POST …/compliance/dsr/exports` (201) and `GET …/dsr/exports/{id}/download` (dsr.manage + step-up).
- Admin writes (step-up): `POST/PATCH/DELETE …/compliance/legal-holds[/{id}]` and `POST …/legal-holds/{id}/notes` (legalhold.manage); `POST …/compliance/erasure-requests` (open, 201), `POST …/compliance/erasure-requests/{id}/{approve,execute,reject,close}` (dsr.manage); execute on an incomplete request retries it with the stored mode, reject on one is 409, close ends one whose remaining producers are unregistered as `closed_partial`.
- Policy engine reads (policy.read): `GET …/compliance/policies[/{id}[/versions]]`, `GET …/compliance/policies/effective?tenantId=`, `POST …/compliance/policies/validate`, `GET …/compliance/retention-classes`, `GET …/compliance/policy-assignments`, `POST …/compliance/policy-assignments/{tenantId}/validate`, `GET …/compliance/change-requests[/{id}]`.
- Policy engine writes (policy.manage + step-up; 202 when the change waits for four eyes): `POST/PUT/DELETE …/compliance/policies[/{id}]`, `PUT/DELETE …/compliance/policy-assignments/{tenantId}`, `POST …/compliance/change-requests/{id}/{approve,reject}`.
- Tier-2 (client surface, `tenant.read`, own tenant only): `GET /v1/tenants/{tenantId}/compliance/policy` — log-content modes and the configured days of the tenant-settable classes, with `retentionEnforced: false` until T4.

## Follow-ups

- **Stored exports (done).** `POST /v1/admin/compliance/dsr/exports` runs `DSRService.ExportAs(subject, operator)` and stores the bundle in the `dsr-exports` bucket (`iface.ObjectStoreProvider` resolved in `Init`; no provider or bucket error means a nil store and `503 compliance.export_storage_unavailable`). The row (`compliance_dsr_exports`, indexes `uuid` unique, `userUuid`, `expiresAt`) expires after `export_retention_days` (read per call, default 30). `DownloadURL` refuses `expiresAt <= now` with `410 compliance.export_expired` before minting anything, so the hourly job `compliance.dsr_exports_cleanup` (10 min timeout, `deleted` detail) only reclaims space; the URL is `blob.ObjectDownloadPresigner.PresignGetDownload` when the store has it (file `dsr-export-<subject8>-<date>.<ext>`), else `PresignGet`, 5 minutes, and the route returns it as JSON (no redirect). The stored exports are a PII producer (`compliance.dsr_exports`, `PIIProducerKeyer` + `PIIProducerCounter`) so an erasure deletes object then row (idempotent; with exports on record and no store the purge fails and the request stays incomplete). Audit `gdpr.dsr.exported` (operator as actor) and `gdpr.dsr.export_downloaded` carry UUIDs only. The inline `/me/dsr/export` is unchanged. **Export vs erasure race:** `Create` refuses with 409 `compliance.export_erasure_in_progress` while the subject has an incomplete erasure request; the producer's purge first upserts a marker `{userUuid, erasedAt}` (`compliance_dsr_export_erasures`, UUID and time only, unique `userUuid`) and `Create` re-reads it after its insert: `erasedAt >= start` means it removes its own object and row and answers the same 409. The cleanup job drops markers older than `export_retention_days`. `gdpr.dsr.export_stored` (exportUuid, format, subject) is emitted after the insert. `export_retention_days` is bounded 1..365. Known limit: the bucket is resolved once in `Init`, not lazily, so storage that comes up later needs a restart.

# Module: Retrieval — corpora, indexing and hybrid search over tenant data

## Purpose

Lets modules declare **corpora** (searchable collections of their own data), indexes them through a transactional outbox and a worker (PR 4), and answers hybrid (dense + BM25) searches with a principal filter (PR 5, see [Search](#search)), over a vector engine behind a driver boundary ([ADR-0023](../../../../docs/adr/0023-core-retrieval-module.md)). Inference is local by default: a corpus is `local_only` unless its owner declares `hosted_allowed`.

## What it owns

PR 3 delivered the registry, the engine contract, the Qdrant driver and the conformance suite; PR 4 added indexing (outbox, worker, corpus state, chunking); PR 5 added search (gate, pinned generation, hybrid arms, erasure veto and source check, rerank, the search log and its retention); PR 6 added erasure finalization, data-subject rights and the compliance wiring; PR 7 added the admin surface (see [Administration](#administration)): four permissions, five operator-host routes under `/v1/admin/retrieval`, one nav item, three Cedar permits and the `/admin/retrieval` console page; PR 8 added the deployment overlay `docker/docker-compose.retrieval.yml` with `./orkestra.sh retrieval …` (see [Deployment](#deployment)), the `bench` package and the `backend/cmd/retrieval-bench` command (see [Benchmark (D14)](#benchmark-d14)). Search still has no generic route (ADR D15); `ConfigSchema` holds five keys in two groups: `indexing` (three) and `search` (two).

## Dependencies and load order

`Dependencies()` is `tenant`, `authz`, `llm`. It sits between `llm` and `compliance` in `cmd/server/catalog.go` (pinned by `core_load_order_test.go`): compliance pushes its audit sink into the retrieval service from its own Init (`iface.AuditSinkSetter`). ## Lifecycle

`Init` reads the operator environment with `os.Getenv` (trimmed). It never contacts Qdrant or `llm` and never returns an error: a core Init error is fatal, so missing infrastructure is a log line.

| Variable | Meaning | Where it comes from | When absent or bad |
|---|---|---|---|
| `QDRANT_URL` | `http(s)` URL of the Qdrant node | `docker-compose.retrieval.yml` sets `http://qdrant:6333`; without the overlay, `docker/.env` through the app compose file (empty default) | INFO "QDRANT_URL is not set..."; engine nil, search answers `ErrRetrievalNotConfigured` |
| `QDRANT_API_KEY` | Qdrant API key | `docker/.env` (`make init`, `openssl rand -hex 32`), passed by the overlay or the app file; `env-validate.sh` refuses `QDRANT_URL` without it | WARN "QDRANT_API_KEY is not set" (URL still used) |
| `QDRANT_COLLECTION_PREFIX` | Collection name prefix, `^[a-z][a-z0-9-]{0,31}$` (no `_`: corpus names may hold one, so `a_b`+`c` would collide with `a`+`b_c`) | `docker/.env` through the app file; the overlay does not set it. `bench` is refused by the benchmark (its scratch prefix) | Default `orkestra`; an invalid value logs a WARN (and an `env-validate.sh` warning) and uses the default |

The inference endpoints (`RETRIEVAL_INFERENCE_ENDPOINTS`, `RETRIEVAL_INFERENCE_API_KEY`) are read by `llm`, not here (see `../llm/AGENTS.md`); the overlay sets both, naming the two TEI services `embed` and `rerank`.

An invalid URL (`qdrant.New` error) logs a WARN and is treated as not configured; the value is never logged, nor is the key. When not configured, `Init` passes an **untyped nil** engine to `services.New` (a typed-nil driver inside the interface would defeat `Service.Engine()`'s `== nil` check).

`Start` calls `Seal()` first (every module's Init has run by then, so a module retried later with `RetryInit` cannot register a corpus), then starts the background jobs under one `context.WithCancel(context.WithoutCancel(ctx))` (the admin enable endpoint passes a request context; precedent `auth/maintenance.go`), so only `Stop` ends them: the index worker when it was built, and the search-log retention loop whenever a database handle is present, engine or not (rows are written either way). A `sync.WaitGroup` over both closes the single `done` channel (precedent `llm/module.go` Start); a second `Start` while running is a no-op. `Stop` cancels the jobs and waits for them or the context. A key held at that moment still ends its lease: `Release`, `Reschedule` and `Requeue` run under `context.WithTimeout(context.WithoutCancel(tctx), 5s)`, while the `HoldsLease` guard and the Load/Embed/engine calls stay on the run context (a cancellation that surfaces at the guard re-queues the key, which then stays leased until expiry). `Init` builds the outbox (`SetOutbox`, so `Enqueue` whenever a database handle is present) and, when an engine is configured and the gateway (`LLMPinnedEmbedder`, `LLMInferenceProfiles`), tenant lister and module status reader resolve, the worker; otherwise the worker is nil and one WARN names what is missing. Config (group `indexing`, read every pass): `worker_lease` (2m, `RETRIEVAL_WORKER_LEASE`), `worker_batch` (32, `RETRIEVAL_WORKER_BATCH`; a value <= 0 falls back to 32, only the upper bound 256 clamps), `worker_poll_interval` (5s, `RETRIEVAL_WORKER_POLL_INTERVAL`). Tests inject an engine through the unexported `Module.newEngine`. The one case where the outbox is not wired is a nil `deps.DB` (production always has one; the repository constructors would panic): `Init` still returns nil with a single WARN naming the missing database, there is no worker, and `Enqueue` returns an error.

`HealthCheck` (only `/v1/admin/modules/health`; `/ready` does not consult modules): engine nil returns nil (not configured is the designed degraded mode); worker nil returns `retrieval: indexing disabled: <missing>`; otherwise `engine.Health` under a 2s timeout, and any error returns `iface.ErrRetrievalUnavailable` itself, because the handler copies `err.Error()` into the response. The driver error goes to the DEBUG log. A healthy engine then reports `Worker.Problems()` as `retrieval: <problem>; ...`.

## Indexing

### For owners

- Call `RetrievalOutbox.Enqueue(ctx, intents...)` with the `mongo.SessionContext` of the transaction that writes the source, so the intent commits or aborts with it. At most 1000 intents per call; `SourceID` 1-256 bytes, valid UTF-8, no NUL; `Revision >= 0`. The tenant must be internal; the corpus must be registered. Validation failures wrap `iface.ErrRetrievalInvalidIntent` / `ErrRetrievalUnknownCorpus`.
- `Revision` is monotonic per item (the outbox keeps the highest with `$max`); a `Load` that returns an older revision than enqueued is retried (`source_behind`). It must stay monotonic per id **across delete and re-create**: an id re-created with a lower revision keeps the old `$max` value and stays `source_behind` forever.
- `Enqueue` keeps an existing backoff (`nextAttemptAt` is only set on insert): an item parked as `invalid_item` and then fixed waits up to 30m before it is retried.
- `Load(ctx, tenantID, ids)` answers only for the tenant passed and reports an absent id as `Deleted`; the worker also treats a missing entry as deleted. `Enumerate(ctx, tenantID, cursor, limit)` pages by an opaque cursor (`""` starts; `Next == ""` ends) and feeds the initial build.
- Item bounds: title cut to 512 bytes (rune boundary) and prefixed to every chunk with `\n\n`; `VisibleTo` <= 1000 and `Subjects` <= 100 entries, each 1-256 bytes; every subject must be erasable (`services.ValidateSubject`, the one rule shared with `DeleteBySubject`): `user:<id>` with a non-empty id free of whitespace and control characters, or `<owner>:<id>` with the owner shape, an id free of whitespace and control characters and an owner that registers a corpus (the item's own corpus owner always counts, so a corpus may carry another registered owner's subjects); fields must be declared, keyword <= 1024 bytes, keyword[] <= 100 elements. A violation is `invalid_item`.

### Per-key protocol

`Claim` sets `dirty=false` and `epoch += 1` and takes the lease (owner, `leaseUntil`). Every write is preceded by `HoldsLease(epoch, owner)`; `Release` and `Reschedule` are fenced on the same pair; `Release` leaves `dirty` untouched, so an intent enqueued during the lease survives, and `Reschedule` sets `dirty: true` with the backoff. A lost lease at a guard re-queues the key (`Requeue`, no release); a `Reschedule` that finds the lease lost does nothing unless the run already wrote to the engine, in which case the key is re-queued. The write deadline is `leaseUntil - lease/4`: Load, Embed and engine calls use a context with that deadline. How long a stale worker can still write after losing its lease is bounded by `FencingWindow(MaxWorkerLease, 30s)` (16m); PR 6 erasure finalization waits that between its passes (see Erasure and data-subject rights).

Processing order of `process` (`worker.go`):

1. Item tombstone covers the key: remove. 2. `Load`: error `source`; a reply that cannot be trusted for the id (two entries for it, an entry neither `Deleted` nor carrying an `Item`, or an `Item.SourceID` naming another id) `invalid_item`; absent or deleted: remove; older revision than enqueued: `source_behind`. 3. Subject tombstone against the item's subjects: remove. 4. `normalizeFields`, `validateItem`: `invalid_item`. 5. `chunk.Split` and build points (no points: remove; text cut by the chunk bounds logs a WARN). 6. If `Applied` has the same generation, profile hash, indexed hash and chunk count (revision ignored): `UpdatePayload`, `DeleteOtherRevisions`, then `Count`; a count equal to the points released as payload-only, otherwise fall through. 7. Embed in batches of 32 (`budget` when the tenant budget is exhausted, else `embed`; a wrong vector count or length is `embed`). 8. `Upsert`, `DeleteOtherRevisions`, `Release` with the new `Applied`.

Backoff `5s * 2^(attempts-1)`, capped at 30m; `invalid_item` always waits 30m; keys are never abandoned. `lastError` and the logs carry only these closed codes: `source`, `source_behind`, `invalid_item`, `embed`, `budget`, `engine`, `deadline` (any error that is a `context.DeadlineExceeded`), `tombstone`. Logs name corpus, tenant, source ID, counts and codes, never text, field values, principals or subjects.

### Passes and the initial build

A pass (`RunOnce`) prepares every corpus (the gate below), claims keys round-robin across at most 64 due tenants until `worker_batch` keys are claimed, then advances initial builds. Passes repeat every `worker_poll_interval`; settings are re-read on every pass and clamped. Fairness state is per process (in memory, each replica keeps its own):

- **Tenant cursor.** `DueTenants(now, corpora, after, 64)` lists tenants with a claimable key whose ID sorts after the cursor, in tenant ID order (never by age, so an old backlog cannot win every pass). The cursor moves to the last tenant that received a claim; it wraps to `""` when the list was shorter than 64 and every listed tenant was offered a claim, it moves to the last listed tenant (past a full list) when nothing in it was claimable, and an empty list after a non-empty cursor is retried once from `""` in the same pass. With more due tenants than `worker_batch`, every tenant gets a claim within `ceil(tenants / worker_batch)` passes; the pass that reaches the tail of the list may claim fewer than `worker_batch` keys.
- **Build pass.** One `Enumerate` page (200 ids, call timeout `lease/2`) per (corpus, tenant) per pass, at most 16 pages per pass overall (a failed call counts); it only enqueues intents, the index pass writes. The sorted (corpus, tenant) pairs are walked from an offset that advances by the pairs visited, so the next pass starts where this one stopped. After an `Enumerate` error the corpus's remaining tenants are skipped for the rest of the pass (one call per pass for a broken source), and if any call failed the next pass instead starts at the pair right after the first failing pair of this pass (mod pair count): advancing by the visited count would leave the offset unchanged after a full walk and starve the tenants behind the failing one; a wholly failing source retries each tenant in turn. A build is remembered as done when this worker's `Advance(done)` succeeds, or when `ClaimBuild` returns nil and `Get` shows `done`; a done build costs no store call afterwards, a build held by another replica costs `ClaimBuild` + `Get` per pass.

### Gate (`prepareCorpus`)

Checks run in this order; the problem text is what `HealthCheck` reports (`%s` corpus, `%q` endpoint).

| Condition | State write | Result | Problem |
|---|---|---|---|
| Owner module not started | none | skip | none (expected while disabled; intents are kept) |
| Endpoint unknown (`ErrLLMNotConfigured`) | error / `endpoint_unknown` | skip | `corpus %s: embed endpoint %q is not configured` |
| Other profile error, or dimensions <= 0 | none | skip | `corpus %s: inference profile unavailable` |
| Endpoint is not an embedding endpoint | error / `endpoint_kind` | skip | `corpus %s: endpoint %q is not an embedding endpoint` |
| `local_only` corpus (or `""`) and endpoint boundary not local | error / `locality` | skip | `corpus %s: local_only corpus uses hosted endpoint %q` |
| No state or no active generation | `EnsureCollection`, then `active`, generation 1, collection `<prefix>_<corpus>_g1` | gate | engine error: `corpus %s: vector engine unavailable` |
| State hash differs from the declared hash | `profile_changed` with `DeclaredProfileHash` (written once) | skip | `corpus %s: ingestion profile changed; indexing paused until a new generation is built` |
| Not active, hash equal | the once-per-process `EnsureCollection` below, then back to `active`, reason cleared | gate | as below |
| Active, hash equal | none (the first time this process gates the generation: `EnsureCollection` with the current filters, analyzer and stored dimensions, so a filter declared after the bootstrap gets its payload index) | gate | engine error: `corpus %s: vector engine unavailable` (skip, retried next pass) |

`profile_changed`: intents are kept, nothing is claimed, the active generation keeps serving, and delivery step 2 (generation build) builds the new generation and drains the intents. Reverting the declaration clears it. `ErrStateExists` / `ErrStateConflict` (another replica moved the state) skip the pass silently.

### Ingestion profile hash

`IngestionProfileHash` = `"ing_"` + hex SHA-256 of the JSON of a private struct `{v, embeddingProfile, analyzer{tokenizer, language, stemming, stopWords}, chunking{strategy, maxTokens, overlap}, enrichment{chatEndpoint, promptVersion}|null}` (tags independent of `iface`). `v` (now 1) is bumped when the code's transformation changes (title prefix, tokenization). Normalization: tokenizer `""` becomes `word`; strategy `""` becomes `none`; `none` zeroes `maxTokens` and `overlap`. `EmbedEndpoint` (the endpoint **name**) is excluded: the resolved profile ID identifies the model, and renaming an endpoint must not start a new generation.

### Chunking and the token approximation

A token is a maximal run of runes for which `unicode.IsSpace` is false, when that run has at most 32 runes; a longer run counts as consecutive 32-rune pieces (the last may be shorter). Whitespace is never a token. One counted token approximates one word; subword tokenizers (bge-m3's XLM-R) produce roughly 1-2 model tokens per word in English and Italian, so a window of `MaxTokens` counted tokens may exceed `MaxTokens` model tokens. Operators choose `MaxTokens <= MaxInputTokens/2` of the embedding profile; the profile's `Truncate` covers any excess (the tail of an over-long window still reaches BM25, not the vector). A chunk's text runs from its first token's first rune to its last token's last rune.

`none`: one chunk, cut at `MaxChunkBytes` (64512). `fixed`: windows of `MaxTokens` with `Overlap`, at most `MaxChunksPerItem` (512), each also bounded by `MaxChunkBytes`. `MaxTokens` is 1-4096 (`chunk.MaxTokensLimit`): registration calls `chunk.Validate` for `none` and `fixed`, so a corpus the chunker would refuse never registers. Provenance offsets `CharStart`/`CharEnd` are rune offsets in the item text.

### Engine additions and config

`Engine.UpdatePayload` replaces `Runtime` and `Fields` of existing points (vector and text kept) only when the stored content hash matches and the stored revision is not higher; it never creates a point and sends every `_rt` field, `page` included. Config group `indexing`: `worker_lease` (2m, clamp 30s-15m, `RETRIEVAL_WORKER_LEASE`), `worker_batch` (32, `RETRIEVAL_WORKER_BATCH`: <= 0 falls back to 32, above 256 clamps to 256), `worker_poll_interval` (5s, clamp 1s-5m, `RETRIEVAL_WORKER_POLL_INTERVAL`). `HotReloadConfig()` is `true` (the worker's settings closure re-reads all three on every pass, so a config write leaves no restart-required flag; any later per-call key, e.g. PR 5's, is covered by the same module-wide flag). `HealthCheck` strings: `retrieval: indexing disabled: <missing>`, `retrieval: the vector engine is unavailable` (the bare `iface.ErrRetrievalUnavailable`), `retrieval: <problem>; <problem>`.

## Search

`iface.RetrievalSearch.Search` on the registered `*services.Service` delegates to the `Searcher` wired by `SetSearch` (no Searcher: `ErrRetrievalNotConfigured`). There is no generic route (ADR D15); a consuming module calls it in process. The only HTTP path that runs a search is the operator diagnostic (`Diagnose`, see [Administration](#administration)), which goes through the same pipeline.

**Never call `Search` with a transaction's `mongo.SessionContext`** (the opposite of `Enqueue`). The success-path search-log insert uses the ctx it was given, so the row would join the caller's transaction and abort with it, leaving a served result without its row (decision 2); the failure-path row is no different, since `context.WithoutCancel` drops only the cancellation, not the session. The code does not detach (controller ruling: document only); callers search before the transaction or after its commit.

### Wiring (`module.go` Init)

- Search is wired **only when `deps.DB != nil`**, `QDRANT_URL` unset included: the search log and `Tombstones` are database-backed. With a nil DB `SetSearch` is not called, `Search` returns `ErrRetrievalNotConfigured`, `Principals` returns `ErrRetrievalForbidden`, and the existing single database WARN covers it.
- `resolveSearchServices(reg)` resolves once, and the worker reuses its `profiles`/`embedder`: `iface.AuthzProvider` and `iface.AuthzRoleLister` from `module.ServiceAuthzProvider`, `iface.TenantProvider` (the membership checker) from `module.ServiceTenantProvider`, and `LLMInferenceProfiles`, `LLMPinnedEmbedder`, `LLMReranker` by type assertion on the `module.ServiceLLMGateway` value. `ModuleStatusReader` comes from `module.ServiceModuleStatus`.
- A missing service stays **nil**. `GetTyped` returns a nil interface for a missing service, and converting a nil interface to another interface (`iface.TenantProvider` to `services.MembershipChecker`) is still nil, so the resolver's `== nil` check holds without a guard; the only hazard is a concrete nil pointer stored in an interface (as with the engine above), which no search wiring does. Missing authz, role lister, tenant provider or module status fail every search closed; missing inference companions degrade it. Init emits **at most one** WARN naming the missing services, never errors, and contacts nothing (ADR D1).
- **Engine-less installs** wire `Tombstones` and the source check like any other, so a search passes the gate and the visibility guard and answers `ErrRetrievalNotConfigured` at step 2, leaving its row (`errorKind` `not_configured`). Wiring no tombstones there would report `ErrRetrievalVisibilityCheck` instead, which misnames the situation.
- The corpus state is read through `services.NewCorpusStateReader(repository.CorpusStates, prefix)`: a missing state or `activeGeneration` 0 is `ErrNoActiveGeneration`; otherwise the pin is `st.Collection` (fallback `engine.CollectionName(prefix, corpus, gen)` when empty) and `st.EmbeddingProfileID`. A corpus in `profile_changed` or `error` that still has an active generation is served; a changed model is caught by the profile-ID comparison (keyword fallback, degraded).

### The pipeline (ADR D5)

| Step | What | Owner |
|---|---|---|
| 1 gate | `RequireInternalTenant` → ctx user and tenant → corpus lookup → `planSearch` (request shape) → corpus permission (`AuthzProvider.HasPermission`) → `filter.Compile`, then the filter's JSON form for the search log (a validated filter `json.Marshal` rejects is `ErrRetrievalInvalidFilter`) → owner module started (`ModuleStatusReader.IsStarted`). A refusal here writes **no** search-log row | `services/search.go` `gate`, `search_params.go`, `filter/compile.go` |
| 2 pin | One corpus-state read per request: collection and embedding profile ID hold for the whole search | `search.go` `pin`, `search_state.go` |
| 3 principals | `PrincipalResolver.Principals` (below); the result must match the caller | `principals.go`, `search.go` `principals` |
| 4 arms | Dense: inference profile of the corpus's embed endpoint, which must be an embed endpoint, match the pinned profile ID and respect locality; then `EmbedWithProfile`. Keyword: the query text (dropped in `dense` mode when the dense arm ran) | `search.go` `denseVector` |
| 5 fusion | One engine query with tenant, principals, compiled filter, weights, `PerArm` and `Limit = min(PerArm, max(4×Limit, RerankK))` | `search.go` `query`, `engine/qdrant` |
| 6 check | Tenant/source-id second guard → erasure veto (`Tombstones.Covered`, one probe per source in first-seen order) → `Source.Visible` under a 2 s timeout, revision must match. A short page after a full engine answer refills **once** with `Limit = PerArm`; only new points are checked, plus the first-call survivors of a source the refill returned a new point of, so a source covered or hidden by then loses every chunk. Point IDs carry no revision, so the worker can replace a point between the calls under the same ID: a source with a point whose refill copy differs from its first-call copy in any `Runtime` field (`sameRuntime`: revision, `VisibleTo`, `Subjects`, provenance) is dropped whole (first-call survivors and new refill points) and not re-checked (the same-revision `UpdatePayload` sharing change included); every returned candidate is the exact copy its last check saw, and a page under `Limit` after such a drop is `degraded` even when the refill came back short. One probe per call suffices because every chunk of an item revision carries the item's subjects (`ingest.go` `buildPoints`) and the revision check keeps one revision per source | `search.go` `fetchChecked`, `checkCandidates`; `tombstones.go` |
| 7 rerank | When the corpus enables it: the first `RerankK = min(200, max(TopK, Limit))` survivors; the head carries the reranker's score | `search.go` `rerank` |
| 8 result | First `Limit` candidates → hits (rank, score, 300-rune snippet, provenance, locality); the search-log row is written **before** the result is returned | `search.go` `toHits`, `logRow`; `snippet.go` |

| Situation | Result |
|---|---|
| No engine (`QDRANT_URL` unset) | `ErrRetrievalNotConfigured` |
| Engine error or state read error | `ErrRetrievalUnavailable` (cause kept in the chain, only its kind logged) |
| No active generation yet | empty hits, `degraded: true` |
| Dense arm cannot run (no companions, profile error, kind, profile-ID mismatch, locality, bad vector: not exactly one, empty, wrong dimensions, or any NaN/Inf value) | keyword-only, `degraded: true` (decision 4 for locality: the text never reaches the endpoint) |

| Page still short after the refill and the last engine answer was full, or the refill dropped a changed source | `degraded: true` (decision 3; D5) |
| Principal resolution error | `principalError`: `ErrRetrievalForbidden` passes through unchanged; anything else (cap, invalid contributor principal, contributor failure, dependency) is `ErrRetrievalUnavailable: principal resolution failed (<kind>)`, keeping only the module's fixed sentinels and `ctx.Err()` in the chain, never the resolver's error; only the kind is logged (decision 6) |

### Principals

`PrincipalResolver` (ADR D10) builds the set from ctx: `user:<uuid>`; `tenant:*` when `TenantProvider.IsMember` says the user is a member; `role:<id>` per `AuthzRoleLister.ActiveRoleIDs` (tenant bindings only, non-expired, active roles); and every registered `RetrievalPrincipalContributor` (`svc.PrincipalContributors`), whose output must match `^[a-z][a-z0-9_]{0,31}:\S{1,200}$` and may not use the reserved prefixes `user`, `tenant`, `role`. The set is deduplicated and sorted. No platform role gets a bypass (`super_admin` resolves like anyone). A nil membership checker or role lister fails every call closed. Above `principal_cap` (config, read per call, default `services.DefaultPrincipalCap` 256, clamp 16-4096) the search fails with `ErrPrincipalCapExceeded` → `ErrRetrievalUnavailable`. A contributor's error may name its principals, so it never leaves the resolver: it becomes `retrieval: principal contributor "<name>" failed` wrapping the unexported `errContributorFailed`, plus `ctx.Err()` only when ctx is done; `ErrPrincipalCapExceeded` and `ErrContributorPrincipal` stay in the chain. The membership checker's and role lister's errors are wrapped, so callers map every resolver error with `principalError` (below) and never log or return its text. `Service.Principals` (the SDK `iface.RetrievalPrincipalResolver`) maps through the same `principalError` as search step 3, so both answer identically.

### Search log

`retrieval_search_log` (`models.SearchLog`), tenant-stamped by `tenantrepo.StampInsert`. One row per search that passed the gate:

- `uuid`, `userUuid` (the searcher), `corpus`, `query`, `filter` (`FilterJSON`: the request's filter as canonical JSON, a **string**: `json.Marshal` of the validated `iface.RetrievalFilter`, so SDK json keys, unset fields omitted, a datetime as RFC 3339; absent without a filter. One shape for the whole retention, whatever Go or BSON type a value had; the PR 6 export decodes it into a generic value with `json.Decoder.UseNumber` so integers stay exact, not into a struct), `mode` (the defaulted request mode, not the arm that answered: `degraded` records a fallback), `principals` (empty when the search failed before step 3), `sourceIds` (returned hits, rank order, unique), `subjects` (sorted union over the returned points only), `hitCount`, `degraded`, `outcome` (`ok`, `degraded`, `error`), `errorKind` (`not_configured`, `unavailable`, `principals`, `visibility_check`, `canceled`; `canceled` is an unavailable stage, embed or engine, failing on a context error), `timings` (ms, measured with the Searcher's `Now`: total, resolve = steps 1-3, embed, engine = every query call, check = veto + Visible, rerank), `createdAt` (`Now().UTC()`), `unchecked` (true on a provisional row awaiting its erasure re-check, absent once confirmed; see "Search-log retraction" below; DSR export and the erasure deletes treat it as an ordinary row).
- **Write before return.** A successful (or degraded) search inserts its row with the request ctx before returning (so never a transaction's `SessionContext`, see above); a failed insert returns no result and `ErrRetrievalUnavailable` + `ErrSearchLogWrite`. A search that failed after the gate is logged best-effort under `context.WithoutCancel(ctx)` with a 5 s timeout (so a cancelled caller still leaves its row); a failed insert there only WARNs and the original error is returned. A nil `Log` fails every search closed before any engine call.
- `slog` never receives the query, snippets, chunk text, principals or subjects: those go only into this collection.
- **Retention**: `search_log_retention_days` (default `services.DefaultSearchLogRetentionDays` 90, clamp 1-3650, read at every run). The loop runs a minute after `Start`, then every 24 h (test seams `Module.retentionFirst`, `retentionInterval`), calls `services.PurgeSearchLog`, which deletes every tenant's older rows in batches of 1000 (`//tenantscope:allow system:`), and logs the count at INFO or the failure at WARN.
- **Unchecked sweep** (its own loop, `uncheckedSweepLoop`, on the same cancel/done as the other jobs, started whenever a database exists, engine or not): one `services.UncheckedSearchLogGrace` (10 min) after `Start`, then every grace, `services.SweepUncheckedSearchLog` deletes every `unchecked` row older than the grace (`PurgeUncheckedBefore`, same batches, `//tenantscope:allow system:`), so a row left unchecked is gone within about 20 minutes. A failure WARNs once per run "unchecked search log sweep failed; retrying at the next run" with a coarse reason and the count, never the error text; a sweep that deleted rows logs the count at INFO. Test seams `Module.uncheckedFirst`, `uncheckedEvery`.
- **Indexes** (`repository.SearchLogIndexes`): `{tenantId, uuid}` unique, `{tenantId, userUuid, createdAt}`, and four system sweeps `{subjects}` (DSR lookup of the people the results named, cross-tenant), `{createdAt}` (retention), `{userUuid}` (PR 6: a searcher's own rows across tenants, which `{tenantId, userUuid, createdAt}` cannot serve) and `{unchecked, createdAt}` partial on `{unchecked: true}` (the sweep of provisional rows).
- **Admin read** (`AdminStore.SearchLog`, `AdminService.SearchLog`): newest first, tenant-scoped, **hides `unchecked` rows and leaves them out of `total`**: a provisional row may name a person whose erasure raced the search, so it is not shown until the re-check confirms it. Cost: a row whose confirm write failed is invisible until the sweep removes it (about 20 minutes). The stored `filter` text is decoded with `json.Decoder.UseNumber` and a second `Decode` must return `io.EOF`, so integers beyond 2^53 stay exact; a filter that does not decode is shown absent with one WARN naming only tenant and corpus. Each entry also carries `filterText`, the stored text verbatim, set only when it decoded (so `filter` and `filterText` are both present or both absent): the console displays it and never parses it, since a browser rounds integers beyond 2^53; `filter` is the decoded value for API consumers. Neither goes into the audit metadata or a log line. A diagnostic run writes an ordinary row (no marker; it is a real search by the administrator).
- **piiscan**: the `userUuid` field makes this a subject-PII collection; the retrieval `PIIProducer` (`services.NewPIIProducer`) covers it, so the baseline carries no `retrieval` line.

## Erasure and data-subject rights

PR 6. Tombstones live in `retrieval_erasures`; this section is how they become a confirmed deletion.

- **Status machine.** `pending -> fencing -> done` (`models.ErasureStatusPending/Fencing/Done`; a row with no status reads as `pending`, `EffectiveStatus()`). `Tombstones.Covered` ignores status: a row vetoes reads and writes from the moment it is inserted and keeps doing so when `done`. Status only tells the finalizer what is left to do.
- **Finalizer** (`services/finalizer.go`, `Finalizer`). A pass is: stage 0 the search-log delete (every pass, by kind: user `DeleteByUserAllTenants`, subject `DeleteBySubject`, tenant `DeleteByTenant`, item none), then in every target collection `DeleteByFilter` followed by `Count` that must be 0 (a `Count > 0` is a failure, a dropped generation `engine.ErrNotFound` holds nothing). Pass 1 moves `pending` to `fencing` (`firstPassAt`, `fenceUntil`, and `nextAttemptAt = fenceUntil` so the sweep returns then); the first pass at or after `fenceUntil` runs again and, once confirmed, marks `done` and audits `retrieval.erasure.finalized`. A `fencing` row claimed while the claimer's clock is still before its `fenceUntil` (skew between replicas) runs no pass and is put back to `fenceUntil` with `MarkFencing` on its own `firstPassAt`/`fenceUntil`, which counts no attempt (`MarkRetry` always counts one). The selector is validated (`SelectorFor`) before stage 0, so a malformed row never widens a delete.
- **Fence = derived, no config key.** `FencingWindow(lease, writeTimeout) = lease + writeTimeout + 30s`, clamped to [1m, 1h]; production calls it with `MaxWorkerLease` (15m) and 30s, so **16m**, independent of the live `worker_lease` (a lease lowered while a longer one is held is covered only by the read veto). A worker's last write is at `leaseUntil - lease/4`, at most claim + 11m15s, which leaves a 4m45s margin. A leftover after the second pass is still never served: tombstones are permanent. `services.IndexingFencingWindow` is deleted.
- **Timing.** Failure backoff `ErasureBackoff(n) = 15s * 2^(n-1)` capped at 15m; sweep every 15s, batch 50, claim hold 2m (the pass runs under `hold - 10s`, the transition under 10s); the inline attempt after a request uses 20s (`piiAttemptTimeout` for the PII producer, `erasureAttemptTimeout` for `DeleteBySubject` and the tenant purge). A row waits out the fence (16m), so retrieval's part of an erasure is confirmed about 16-17 minutes after it was recorded (longer when the engine is down); a compliance request that waits on it completes at compliance's next automatic run, typically about 30 minutes after it was recorded.
- **Tombstone creation is at-least-once.** `Ensure*` are upserts on a natural key that no unique index covers (`ErasureIndexes`), so two writers racing on the same erasure (for example replicas running `ReconcilePurgedTenants` together) can insert two rows. Duplicates are harmless: each vetoes on its own, `ListUser` returns all of them so the PII producer's `Pending` stays true until every one is `done`, the sweep finalizes each, and `TenantTombstoneIDs` deduplicates; the cost is a second `retrieval.erasure.recorded` event and a second finalization. No unique index is added (it would need a duplicate check on existing data).
- **Claim CAS, multi-replica safe.** `ClaimDue` is one atomic `FindOneAndUpdate` over due rows that sets `nextAttemptAt = now + hold` (a status-less legacy row is claimable and stamped `pending`); only the winner steps, and `MarkRetry/MarkFencing/MarkDone` are fenced on the claimed `nextAttemptAt`, so a replica whose claim expired cannot overwrite the newer owner's outcome. Index `{status, nextAttemptAt}` serves the sweep.
- **No engine.** Engine nil and no collection recorded (or listable): stage 0 runs and the row goes `done` at once (nothing can have been written). Engine nil **but collections recorded** stays `pending` and retries: the data may be there and cannot be confirmed gone.
- **Retention (decision).** No tombstone is ever deleted in step 1, whatever kind or status: user tombstones cover present and future corpora and tenants; subject and tenant tombstones cover owner rows the module cannot see disappear (a purge crypto-shreds keys, it does not delete owner rows, and `Enumerate` in a rebuild could reach them); item tombstones stay because `RetrievalSource.Load` reports soft-deleted, restorable and permanently removed items alike as `Deleted` (D7). A `done` tombstone keeps vetoing.
- **Search-log retraction (durable).** When the Searcher has a retractor (`SearchLogRetractor`: `DeleteRow` + `MarkChecked`, satisfied by `*repository.SearchLog`) and tombstones, every row (success, degraded or the best-effort failure row) is inserted with `unchecked: true`; then `Searcher.retract` re-checks the row's subjects and searcher against the tombstones: covered -> `DeleteRow`, not covered -> `MarkChecked` (`$unset unchecked`, tenant-scoped like `DeleteRow`). This closes the race between a search and an erasure (either the re-check sees the tombstone, or the eraser's delete sees the row). Cost: one `Tombstones.Covered` lookup and one write per logged search. A failed re-check is retried once; if it fails again, or the delete or the mark fails, the row simply stays `unchecked` with a WARN "the row is swept as unchecked" (corpus and tenant, no text), and the unchecked sweep deletes it within about 20 minutes (older than `UncheckedSearchLogGrace`, 10 min, swept every 10 min); finalizer stage 0 also still deletes it while the erasure is not `done`. So the outcome no longer depends on the erasure still being finalized. Trade-off (fail-closed for privacy, replaces ruling R-F3): an unchecked row is dropped even if nothing covered it, so rarely a legitimate audit row is lost when Mongo failed between insert and confirmation. A Searcher whose log cannot settle rows (no `DeleteRow`/`MarkChecked`, or no tombstones) writes confirmed rows and does no re-check. The `Search` return value is unchanged: hits that passed the veto were served legitimately before the erasure.
- **PII producer `retrieval`** (`services.NewPIIProducer`, registered as `iface.PIIProducer`, so compliance's DSR walks it). Export: the user's own searches (tenant, corpus, query, filter, result count, time) and the searches by others that returned the user as a subject (tenant, corpus, time only; other people's data is never exported); `(nil, nil)` when empty; the filter is the stored JSON decoded with `UseNumber`. Purge: both erase modes delete (vectors are personal data), in order: global user tombstone (`EnsureUser`, idempotent), delete the user's search-log rows in every tenant, inline `Attempt`; `Pending` stays true until the user tombstone is `done`, so the compliance request stays `incomplete` and compliance calls again. An error is returned with what was already deleted (the `iface.PIIProducer` contract; compliance adds it to the request's count): a failed log delete reports its committed batches (`Collections` `[retrieval_search_log]` when any), a failed `ListUser` after it the full count and both collections, as on success but without `Pending`. An empty uuid is refused (`ErrErasureEmptySubject`) so the selector can never become `user:`.
- **`DeleteBySubject`** (`iface.RetrievalSearch`, `(*Service).DeleteBySubject` -> `ErasureService`): subject `<owner>:<id>` checked by `ValidateSubject`, the rule indexing applies to item subjects, so every non-user subject an item can carry is erasable: at most `MaxRefBytes` (256) bytes, owner matching the corpus owner shape and equal to the owner of a registered corpus, id without whitespace or control characters; owner `user` refused (platform users are erased only through compliance, D12), tenant id required. Records a subject tombstone (`EnsureSubject`, idempotent), audits `retrieval.erasure.recorded` the first time, and runs an inline pass; only the tombstone write can fail the call. A service built without erasure returns `iface.ErrRetrievalNotConfigured`.
- **Tenant purge.** `iface.TenantPurgeHooks` (tenant, on offboarding) calls `ErasureService.PurgeTenant`: tenant tombstone written in up to 3 tries (100 ms then 400 ms apart) on a context detached from the request with a 30 s bound, then an inline pass; a failure is returned to tenant's cascade, which audits it as `tenant.cascade.hook_failed` against the tenant. `iface.PurgedTenantIDLister` feeds `ReconcilePurgedTenants`, which writes the tombstone of every purged tenant that has none (hook failed or never ran, or the tenant was purged before PR 6); the module runs it a minute after `Start`, then every 10 minutes. Without the hook registrar or the lister Init logs one WARN "tenant purge erasure is not fully wired" naming what is absent. The finalizer runs even without an engine.
- **Audit.** `retrieval.erasure.recorded` and `retrieval.erasure.finalized` (`services/audit.go`) go through `AuditRelay`, which forwards to the sink compliance pushes (`iface.AuditSinkSetter`; before that, or without one, every emit is a no-op). Metadata never carries a subject value, a query or a source id. `AuditRelay.EmitOutcome` (actor, tenant, kind and client IP from the ctx; outcome `success` or `failure`; `Emit` is `EmitOutcome` with `success`) is what PR 7's admin actions use; the module's own events use `EmitSystem` with the tenant id. `wireErasure` returns the one relay and `Init` hands it to `NewAdminService`, so a sink compliance pushes after `Init` reaches the admin events as well; the admin service does not resolve `module.ServiceAuditSink` itself. `NewAdminService` panics on a nil `Audit` (a private relay would drop every admin event unseen), and `TestModule_AdminAuditReachesTheLateSink` pins the wiring.
- Test seam: `engine/enginefake` is an in-memory `engine.Engine` that fails closed like the driver.

### Admin invariants

- No admin route returns content or scores except diagnostics, which returns snippets and per-stage scores (`dense`, `keyword`, `fused`, `rerank`, final) for the caller's own principals. The search log returns the query text, the returned source ids and the subjects, which is why it carries its own permission, MFA, step-up and an audit event.
- `Diagnose` (`services/diagnostics.go`) shares `Searcher.search(ctx, req, diag)` with `Search`: it only sets `engine.Query.Diagnostics` and records scores, so the gate, the pinned generation, the principal filter, the erasure veto, the `Visible` check and the retraction run unchanged. No bypass. It writes a normal search-log row (and goes through the unchecked/retraction path).
- Every admin action emits an audit event through the shared relay (`EmitOutcome`), success and failure: `retrieval.diagnostics.run` (resource `retrieval_corpus`: mode, limit, query rune count, hits, degraded; never the query or the filter), `retrieval.corpus.dropped` (collections and deleted outbox and progress row counts once known) and `retrieval.searchlog.read` (resource `retrieval_search_log`: the requested `userUuid`, `since`, `until`, `limit`, `offset` and the number of rows returned, never a row). One rule for all three: the internal-tenant check (`requireOperator`) runs first and a refusal there is not audited (it touched nothing, and the middleware already logged it); neither is the search-log read's own request-shape re-check (`limit`, `offset`, `since` after `until`), which runs before any data access. Every request past that point is audited exactly once, `success` or `failure`, and a failure carries `metadata.reason`, the error code the handler answers with (`AuditReason`). That includes the pipeline's refusals in Diagnose (the D7 corpus permission, an unknown corpus, an invalid filter or request, locality, an owner not running) and the drop's `corpus_registered` and `corpus_not_found` refusals. The relay is resolved at emit time, so a sink pushed after `Init` is used.
- Orphan drop order: engine collections (generations 1 to the active one, plus the state's own collection name; a missing collection is fine), then the outbox and tenant-progress rows, and the state row **last**, by compare-and-delete on its `version`. The state row is the operator's handle on the orphan, so a failure midway leaves it and the drop can be retried. If the compare misses, a vanished row counts as success and a moved version means another replica registered the corpus again (`409 retrieval.corpus_registered`). Search-log rows and erasure tombstones are never touched. Retrying a drop of an already dropped orphan answers `404`.
- Drop an orphan only after **every** replica runs a binary without the corpus registration. The "registered" check is per process, so a replica that still registers the corpus would rebuild it.
- `AdminService` reads the engine and inference health with short timeouts, never at `Init` (D1), and tenant scoping comes from the ctx (`tenantrepo`); new cross-tenant Mongo calls carry their own `//tenantscope:allow system:`.

## Corpus registration rules

`RegisterCorpus` is syntax-only, runs during any module's `Init`, never contacts the engine or llm, and fails once sealed. Rules (`services/registry.go`):

- Name `^[a-z][a-z0-9_]{0,31}$`, unique; owner `^[a-z][a-z0-9_-]{0,63}$`; permission `a.b[.c[.d]]` lowercase; `Source` required.
- At most 32 filters; names `^[a-z][a-zA-Z0-9_]{0,63}$`, unique, known type, description 1..500 bytes.
- `embedEndpoint` required (no whitespace, <= 64 bytes). Tokenizer `word` (default) or `multilingual`; stemming needs a Snowball language, stop words a stop-word language (Qdrant 1.20 enums). Chunking `none` (no sizes) or `fixed` (`maxTokens` 1..4096, `0 <= overlap < maxTokens`, checked by `chunk.Validate`); `hierarchical` and enrichment are refused until delivery step 3.
- Locality `""` becomes `local_only`; fusion defaults 1/1/50 (weights in (0,10], candidates 1..500); rerank `topK` defaults to 20 (1..200), enabled needs an endpoint.
- The registry stores a normalized deep copy. Locality against the actual endpoints is checked at profile resolution (PR 4/5), not here.

## Engine contract

- Import direction: `engine` -> `iface`, `uuid`, stdlib; `engine/qdrant` -> `engine`, `iface`; `enginetest` -> `engine`, `iface`; `filter` -> `engine`, `iface`; `services` -> `engine`, `filter`, `models`, `iface`; `module.go` -> `services`, `engine`, `engine/qdrant`, `repository`; `bench` -> `engine`, `iface`, stdlib. `engine` never imports a driver, and consumers outside this module never import `engine`, with one documented exception: the module's own tool `backend/cmd/retrieval-bench` -> `bench`, `engine`, `engine/qdrant`, `iface` and `llm/installation` (it must parse `RETRIEVAL_INFERENCE_ENDPOINTS` with the backend's own parser, so it measures the endpoints the backend would load).
- Values: keyword `string`, keyword[] `[]string`, integer `int64`, float `float64`, bool `bool`, datetime `int64` Unix **milliseconds** UTC (`Point.Fields`) and `float64` milliseconds (`Range`). Datetime fields get an integer payload index, so range compilation needs no field-type lookup.
- Payload: `_rt` = module-only runtime fields plus `_rt.text` (the indexed text); `f` = declared filter fields. A user filter field is always rendered as `f.<name>`, never a raw key.
- `Upsert` replaces a point's whole payload (a field the new write omits is gone; conformance `UpsertReplacesPayload`). `UpdatePayload` (the payload-only path) **merges into `_rt`**: the driver sends Qdrant `set_payload` with `"key": "_rt"` (a top-level `set_payload` of `_rt` would replace the object and drop `_rt.text`, the indexed text; verified on Qdrant 1.20) and replaces `f` whole with a second `set_payload`, both filtered on the point id, the stored `_rt.contentHash` and `_rt.sourceRevision <= ` the incoming one. A merge never clears a key it omits, so the driver sends every `_rt` field, `page` included, through its own shape without `omitempty` (ruling R1).
- Point ids: UUIDv5 (`engine.PointID`) over `tenantID\x00corpus\x00sourceID\x00ordinal`. Collection names: `<prefix>_<corpus>_g<generation>`.

## Qdrant driver

- **Floor v1.20.0**: BM25 scoring on the full-text index. `Health` parses the server version as `major.minor` and refuses older servers (the error carries the parsed numbers, never the server string), then lists collections to prove the API key works.
- **Errors** never contain the URL, the key or a response body (a non-2xx body is drained, at most 64 KiB, for connection reuse, never read into the error). Classification:
  - `engine.ErrUnavailable`: network, dial or TLS failure; a timeout (the caller's deadline or the driver's `Timeout`, also `context.DeadlineExceeded`); 5xx; 401/403 (wrong API key); 429; a response over `MaxResponseBytes`; an undecodable body (every 2xx reply, including those of writes and deletes, must be a JSON object with `result` or `status:"ok"`, so a proxy's HTML 200 is an outage, not a success); `Health` on a server older than 1.20.
  - `engine.ErrNotFound`: 404, i.e. a missing collection (`DropCollection` treats it as success).
  - `context.Canceled` (not `ErrUnavailable`): the caller canceled the context.
  - Neither sentinel (a refusal): any other 4xx, and every check made before a request (empty collection name, invalid point, selector or query, malformed filter (including a composite node carrying its own Match, Range or Exists), dimension mismatch on an existing collection).
- **Fail closed**: `Query` requires a tenant and non-empty principals; selectors with `SourceIDs` set but empty (or holding an empty id), or with `SourceIDs` but no `TenantID` (source ids are tenant-local), are refused, while a `Subject`-only selector stays tenant-less on purpose (global user erasure); a malformed compiled filter is refused rather than dropped; the scope filter is repeated on every prefetch arm and at top level, and a candidate scope backstop drops (and WARNs about) any returned candidate outside tenant/principals.
- **BM25 statistics** are tenant-scoped via `params.idf.corpus` on the keyword arm; collections use one shard so statistics stay exact.
- **Conditional upsert**: a write applies only when the stored `_rt.sourceRevision` is <= the incoming one, so a request carries a single revision (groups are sent in order; a failure in a later group leaves earlier groups written). Limitation: a point that does not exist is inserted whatever its revision, so a stale writer racing a delete can recreate a point; detection is by revision on read (ADR D11).

## Deployment

The opt-in overlay `docker/docker-compose.retrieval.yml` (ADR D9) runs `qdrant`, `tei-embed` (`BAAI/bge-m3`) and `tei-rerank` (`BAAI/bge-reranker-v2-m3`) on `retrieval-net` (`internal: true`, shared with the backend, no host port in any environment); two seed services (profile `retrieval-seed`) download the weights over `retrieval-egress` and are removed before the serving containers start. Lifecycle is `./orkestra.sh retrieval up|down|status|info|logs|bench`; compose details, the hardening test and the variables are in `docker/AGENTS.md` ("Retrieval overlay"), the operator guide in `docs/site/operating/retrieval-overlay.mdx`. What matters to this module:

- The overlay sets `QDRANT_URL`, `QDRANT_API_KEY`, `RETRIEVAL_INFERENCE_ENDPOINTS` and `RETRIEVAL_INFERENCE_API_KEY` on the backend; nothing here reads a compose file, so `Init` behaves the same with an external Qdrant/TEI set in `docker/.env`.
- TEI runs with `--max-batch-tokens ${TEI_MAX_BATCH_TOKENS:-2048}`, which TEI also applies as the max input length (`/info` `max_input_length`, the profile's `MaxInputTokens`). At the default, a corpus's `fixed` chunks stay at `MaxTokens <= 1024` ([Chunking](#chunking-and-the-token-approximation)).
- The reference models are provisional until the representative D14 benchmark (ADR D4); the overlay pins them by revision, and the hardening test fails when the endpoints JSON and the TEI command disagree.
- CPU rerank is slow: the 2026-10-30 smoke run (reference host, contended) measured TEI rerank calls of 20 candidates at median 15.9 s / p95 47.6 s and a hybrid+rerank search p95 of 54 s, against ~350 ms for hybrid. Keep rerank off (the corpus default) unless the rerank endpoint is a GPU or external server; the operator page has the full table.

## Benchmark (D14)

`bench/` + `backend/cmd/retrieval-bench`, run with `make retrieval-bench` (= `./orkestra.sh retrieval bench [flags]`: `go run` inside the backend container, overlay up, only where the backend runs from the checkout: development and the base's hot-reload staging, not a staging that runs the production image, which the command detects and refuses; `RETRIEVAL_BENCH_ARGS` passes flags). It talks to TEI over HTTP and to Qdrant through the `engine/qdrant` driver, not through the `llm` gateway (which would need MongoDB and ledger rows): it measures the models, the engine arms and fusion.

- **Endpoints.** `-embed-endpoint`/`-rerank-endpoint` (defaults `embed`/`rerank`) are resolved with `installation.Parse(raw, getenv, ENV in {staging, production})`, so prefixes, `normalize`, `truncate` and `apiKeyEnv` are exactly the backend's; the run exits 1 when `/info` reports another `model_id`/`model_sha` than declared. `-embed-url`/`-rerank-url` synthesize `{URL, RETRIEVAL_INFERENCE_API_KEY, Normalize, Truncate}` with no declared identity and **no prefixes** (an e5-style model needs them: declare it as an endpoint instead).
- **Scratch data.** One collection `engine.CollectionName("bench", "scratch"+tag, 1)`, tag `^[a-z0-9]{1,24}$` (default base-36 UnixNano), single tenant (`-tenant`, default `t-bench`); `QDRANT_COLLECTION_PREFIX=bench` is refused. The drop is deferred before `EnsureCollection` and runs under `context.WithoutCancel` + 30 s; a failed drop is `errors.Join`ed with the run's error (never lost when the run already failed). The CLI cancels on SIGINT, SIGTERM and SIGHUP; `retrieval bench` drops `exec -T` on a terminal so Ctrl-C reaches it. Without a TTY the bench may keep running in the container and still drops its collection; only a killed process or a failed drop leaves one behind (the operator page shows how to check and how to delete it).
- **Text.** Indexed and embedded text is `Title + "\n\n" + Text` (the production chunk shape); `DocumentPrefix`/`QueryPrefix` go only into the embedding input.
- **Report.** recall@k and nDCG@k from the first sample of each judged query; p95 over queries × `-repeat`, timing `rank` only (query embedding, engine, rerank): the visibility bookkeeping (`account`, an id → index map built by `LoadFixture`) runs after the clock stops; `VisibilityViolations` summed over every sample and checking principals only (the driver's own backstop drops out-of-scope candidates, so live it must be 0); `ItemsPerSecond` includes `EnsureCollection`; `PeakRSSBytes` is the bench process's VmHWM, not TEI's. `-json` (mode 0600) marshals durations as nanosecond integers. Exit 0 ok, 1 run error or violations, 2 usage (a stray positional argument included: flags only) or `ENV=production` (refused by the binary too, not only by `orkestra.sh`).
- **Logging.** Output goes to stdout/stderr through `fmt`, never `slog` (logscope).

## Invariants

- The admin surface is exactly the four permissions, five operator-host routes, three Cedar permits and one nav item of [Administration](#administration); search has no generic route (ADR D15). The Qdrant settings are operator environment only (ADR D4/D9). `ConfigSchema` has the three indexing keys and the two search keys.

- `Init` never contacts Qdrant or an inference endpoint, and never returns an error.
